## 一、注册

`POST /api/user/register` → `{username, password, nickname}` → `{code:200}`

### Service 五步

1. **判空**：`StringUtils.hasText()` 同时挡 null / `""` / 纯空格
2. **查重**：`selectCount(...eq(User::getUsername, ...))`
3. **重复抛异常**：`USERNAME_EXISTS(1004)`
4. **组装实体**：`password` 用 `passwordEncoder.encode()`，`nickname` 空则兜底用 `username`，`role=0` / `status=1` 显式设置
5. **插入**：`userMapper.insert(user)`

### 四个关键点

**① `createTime` / `updateTime` / `deleted` 一个字都不用写**

建表时有 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP` / `DEFAULT 0`。MyBatis-Plus 默认 `NOT_NULL` 策略，值为 null 的字段**根本不会出现在 INSERT 语句里**，数据库默认值自然生效。

实际执行的 SQL 只有 5 列：

```sql
INSERT INTO `user` (username, password, nickname, role, status) VALUES (?, ?, ?, ?, ?)
```

**② `nickname` 必须兜底**

前端注册页只有用户名 / 密码 / 确认密码三个输入框，`form = reactive({ username: '', password: '', confirm: '' })`，**压根不传 nickname**。不兜底的话数据库里就是 null，首页问候语会变成"你好，null"。

**③ 密码只能存密文**

`passwordEncoder.encode()` 输出的 `$2a$10$...` 是 **60 位**。如果看到 68 位带 `{bcrypt}` 前缀，说明 `PasswordEncoder` Bean 没生效，用的是默认的 `DelegatingPasswordEncoder`。

**④ 查重不是安全边界**

真正保证用户名唯一的是数据库 `uk_username` 索引。并发时两个请求可能都通过查重，最后由索引兜底报 `DuplicateKeyException`。**代码查重只是把数据库的硬报错换成用户看得懂的提示。**

> [!note] 已知副作用
> `uk_username` + 逻辑删除的组合：账号被逻辑删除（`deleted=1`）后，同名无法再注册。查重 SQL 自动带 `deleted=0` 查不到，但 insert 会撞索引。毕设阶段不处理。

### 管理员账号

```sql
INSERT INTO `user` (username, password, nickname, role, status, deleted)
VALUES ('demo', '$2a$10$...', 'lzj', 1, 1, 0)
ON DUPLICATE KEY UPDATE password = VALUES(password), role = 1, status = 1, deleted = 0;
```

BCrypt 密文必须用项目同一个 `BCryptPasswordEncoder` 生成（60 位，`$2a$10$` 开头）。

## 二、登录

`POST /api/user/login` → `{username, password}` → `{token, user}`

### Service 六步

1. **判空**
2. **按用户名查**：`selectOne(...eq(User::getUsername, ...))`
3. **用户不存在 → 抛 `PASSWORD_ERROR`（不是 `USER_NOT_FOUND`）**
4. **校验密码**：`passwordEncoder.matches(明文, 密文)`
5. **状态检查**：`status == 0` → `ACCOUNT_DISABLED`
6. **签发 token + 写 Redis + 组装 `LoginVO`**

### 两个安全设计（答辩必问）

> [!important] ① 用户不存在也返回"用户名或密码错误"
> 这叫防**用户名枚举**。如果明确说"用户不存在"，攻击者拿一个用户名字典就能批量摸出哪些账号真实存在，之后只针对这些账号撞密码，效率高一个数量级。
> 所以 `USER_NOT_FOUND` 这个错误码留着给别的场景（查详情、管理端），登录这条路上不用。

> [!important] ② 状态检查必须放在密码校验之后
> 如果先查 status，就等于在对方还没证明身份时，告诉他"这个账号存在且被停用了"——同样泄露信息。
> **先证明你是谁，再告诉你账号状态。**

另外：`matches(明文, 密文)` 的**参数顺序不能反**，反了永远返回 false 且不报错。也**不能用 `equals`**——BCrypt 每次加密同一密码结果都不同（带随机盐），只能靠 `matches` 反推验证。

### JWT 签发

```java
public String createToken(Long userId, String username, Integer role) {
    Date now = new Date();
    Date expiration = new Date(now.getTime() + expire * 1000L);   // 注意 1000L
    return Jwts.builder()
            .subject(String.valueOf(userId))     // 主体放 userId
            .claim("username", username)
            .claim("role", role)                 // 管理端判断权限用
            .issuedAt(now)
            .expiration(expiration)              // 传 Date，不是时间戳
            .signWith(key())                     // 传 SecretKey，不是字符串
            .compact();
}

public Claims parseToken(String token) {         // 失败返回 null，不抛异常
    return Jwts.parser().verifyWith(key()).build()
            .parseSignedClaims(token).getPayload();
}
```

- `parseToken` 内部 catch `JwtException | IllegalArgumentException` 返回 `null`，2.3 的过滤器只需判断 `if (claims == null)`
- `expire * 1000L` 必须 long 运算。写成 `1000` 遇到大值会 int 溢出成负数，token 一签发就过期
- 密钥 65 字符 → jjwt 自动选 **HS512**（不是 HS256）

### Redis 白名单

```java
stringRedisTemplate.opsForValue().set(
        "wardrobe:login:token:" + token,   // key
        String.valueOf(user.getId()),      // value：只存 userId
        userJwtUtil.getExpire(),           // 7200，从 yml 注入
        TimeUnit.SECONDS);
```

最终 Redis 命令：

```
SET "wardrobe:login:token:eyJhbGci..." "3" EX 7200
```

实测验证：

```
GET  → "3"        （demo 的 userId）
TTL  → 7199       （7200 少 1 秒是执行耗时）
```

**三个设计点：**

- 用 **`StringRedisTemplate`** 不用 `RedisTemplate`。后者用 JDK 序列化，key 在 `redis-cli` 里是一堆 `\xac\xed` 乱码
- value 只存 **userId**。因为 JWT payload 里已经有 username 和 role，Redis 只当"是否有效"的开关，不用重复存数据
- 用带 timeout 的 `set`，**不要 `set` + `expire` 两步**。非原子操作，中间被中断会留下一个永不过期的 key = 安全事故

### 为什么 JWT 还要配 Redis

| | 只用 JWT | JWT + Redis 白名单 |
|---|---|---|
| 防伪造 | 可以 | 可以 |
| 验真伪要不要查库 | 不用（纯计算） | 要（多一次 Redis 查询） |
| 能主动踢人下线 | **不能** | 可以（删 key） |
| 改密码 / 封号立刻生效 | **不能** | 可以 |
| 退出登录 | 只能前端删本地 token，服务端管不了 | 删 key |

**JWT 证明这张凭证没被伪造，Redis 证明它现在还有效。**

> [!tip] 多端登录
> 每次登录都签发新 token 且不删旧的，所以同一账号可以在多处同时在线。要做"单端登录"需额外维护反向索引 `wardrobe:login:user:{userId}` 记录该用户的所有 token。

## 三、支撑设施（简）

### 实体与 Mapper

6 个实体，统一 `@Data` + `@TableName` + `@TableId(type = IdType.AUTO)`。

**逻辑删除只给 `User` / `Clothing` / `ClothingCategory` / `Outfit`。** `ClothingTag` / `OutfitItem` 走物理删除——`outfit_item` 上有 `uk_outfit_role (outfit_id, role)`，做逻辑删除后"删掉旧上装换新的"会撞索引。

`User.password` 加 `@JsonIgnore`，实测返回的 user 对象里确实没有 password 字段。

### 统一异常体系

```
common/  Result · ResultCode · BusinessException · GlobalExceptionHandler
```

错误码分段：**4xx 通用 / 1xxx 用户 / 2xxx 衣柜 / 3xxx 搭配**。`UNAUTHORIZED` 必须是 `401`，因为前端拦截器写死了 `if (res.code === 401)` 就清 token 跳登录。

分工：**Service 抛异常 → Controller 只做三件事（接参数、调 Service、包 Result）→ 全局处理器统一转**。

Service 不返回 `Result`，否则业务层就依赖了 Web 层的响应格式。

## 四、踩坑记录

### 1. Lombok 静默失效 → 接口全返 406

**现象**：所有接口返回 `406 Not Acceptable`，但错误页的 JSON 能正常输出。

**排查**：`javap -p -classpath target/classes ...Result` 发现 `@Data` 的 getter **一个都没生成**。Jackson 认为这个类没有可序列化属性，判定"无法写出"，抛 406。

**根因**：Maven 编译时 `JAVA_HOME` 没设好，落到了系统 PATH 里的 **JDK 25**。**从 JDK 23 起 javac 默认 `-proc:none`，注解处理器不再自动执行**，Lombok 静默失效——编译不报错，运行时才炸。

**修复**：pom 里显式声明

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path><groupId>org.projectlombok</groupId><artifactId>lombok</artifactId></path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
```

### 2. HikariCP 懒加载 → 假的"启动成功"

配了 `hikari.initialization-fail-timeout: -1` 后连接池完全懒加载。**没有代码请求连接时连接池根本不创建**，密码填错也显示"启动成功"。

**修复**：加 `/api/health/db` 主动执行 `select 1` 才算真验证过。

### 3. Knife4j 的两个版本陷阱

- **groupId 变了**：4.5.0 起从 `com.github.xiaoymin` 改成 **`com.github.xingfudeshi`**
- **4.4.0 及更早自带 springdoc 太旧**，与 Spring Framework 6.2+ 不兼容，启动报 `NoSuchMethodError`，必须 4.6.0

### 4. jjwt 0.12.x 与网上教程完全不同

苍穹外卖、黑马点评用的都是 **0.9.1**，照抄必编译失败：

| 0.9.x | 0.12.x |
|---|---|
| `setSubject` | `subject` |
| `setClaims` | `claims` |
| `setExpiration` | `expiration` |
| `setSigningKey` | `verifyWith` |
| `signWith(SignatureAlgorithm, byte[])` | `signWith(SecretKey)` |
| `parseClaimsJws(t).getBody()` | `parseSignedClaims(t).getPayload()` |

另外 HS 算法要求密钥 **至少 32 字节**，太短第一次签发时抛 `WeakKeyException`。

### 5. GlobalExceptionHandler 漏了 `@RestControllerAdvice`

只写了方法上的 `@ExceptionHandler`，类上没加 `@RestControllerAdvice`。它就成了普通 Java 类，**注解完全不生效**，异常照样走默认 500。

### 6. `void` 方法不能 `return` 值

`public void register(...)` 里写 `return Result.fail(...)` 编译不过。解法不是改返回类型，而是**用异常**。

### 7. Boot 3 的 Redis 配置前缀变了

黑马点评是 `spring.redis`（Boot 2.x），Boot 3 必须 **`spring.data.redis`**。写错配置**被静默忽略**，客户端连默认 `localhost:6379` 报超时，报错信息完全不提配置写错了。

### 8. 前端读的是响应体里的 code，不是 HTTP 状态码

```js
if (res.code !== 200) {
  if (res.code === 401) { 清 token; 跳登录 }
}
```

`res.code` 来自响应体 JSON。后端返回 HTTP 401 时 axios 走 `error` 分支，**清 token 跳登录的逻辑根本不执行**。

> [!warning] 2.3 必须注意
> 未认证时返回 **HTTP 200 + body `{"code":401,"message":"未登录"}`**。

## 五、关键决策（答辩可能问）

| 决策 | 选择 | 理由 |
|---|---|---|
| 主键 | `BIGINT AUTO_INCREMENT` | 雪花 ID 19 位超出 JS 安全整数，前端精度丢失 |
| 密码存储 | BCrypt | 随机盐 + 可调强度 + 抗彩虹表，MD5 无盐已淘汰 |
| 鉴权 | JWT + Redis 白名单 | 兼顾"免查库验真伪"和"能主动作废" |
| 注入方式 | 构造器注入 | 字段可 `final`、依赖缺失编译期报错、便于单测 |
| 逻辑删除范围 | 只给三张主体表 | `outfit_item` 有唯一索引，会和逻辑删除打架 |
| 错误码 | 分段枚举 | 看 code 就知道哪个模块 |
| 季节存储 | 位标识 1/2/4/8 | `season & ? != 0` 即可查多选，不用关联表 |
| Redis 库 | 1 号库 + 项目前缀 | 0 号库给黑马点评；上云只有单库靠前缀区分 |
