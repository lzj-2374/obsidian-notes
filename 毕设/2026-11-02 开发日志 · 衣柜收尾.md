## 一、修改衣物

`PUT /api/clothing/{id}`，body 是前端 `{ ...clothing }` 整个对象。

### 五步

1. **查归属**：`id + userId` 两个条件查一次，查不到抛 `CLOTHING_NO_PERMISSION`
2. **组装**：`BeanUtils.copyProperties(dto, clothing)`，把 dto 字段覆盖到查出来的对象上
3. **更新**：`clothingMapper.updateById(clothing)`
4. **删旧标签**：`DELETE FROM clothing_tag WHERE clothing_id = ?`
5. **插新标签**：遍历 `dto.getTags()`，**每条先 `setId(null)`** 再 insert

### 三个关键点

**① 不要 `setId(userId)`**

`clothing` 是从库里查出来的，它的 `id` 本来就对。`BeanUtils.copyProperties(dto, clothing)` 只覆盖 dto 里有的八个字段，dto 没有 id，所以 id 保持原值。

手贱加一句 `clothing.setId(userId)`，就等于告诉 `updateById`“去更新 id 等于 userId 的那一行”，改到别人衣服上去了。

**② 标签的 `setId(null)` 必须写**

前端传回来的 `tags` 是从详情接口查的，每个元素带着原主键：

```json
"tags": [
  { "id": 11, "clothingId": 5, "tagType": 1, "tagValue": "休闲" }
]
```

不置空直接 insert，MyBatis-Plus 会当成“插入一条主键为 11 的记录”，而 11 号刚在第四步被删掉、自增序列很可能马上又要发到 11——直接主键冲突。

**③ 标签为什么用「全删重插」而不是逐条比对**

逐条比对要先查旧标签、跟新标签做差集、算出哪些删哪些加，代码长还容易漏。全删重插一行 `DELETE` + 一个循环就完事，数据量小（一件衣服最多十来个标签）时这就是标准做法。

## 二、删除单件

`DELETE /api/clothing/{id}`。

### 关键设计：引用 vs 从属

删除之前要判断“这件衣服有没有被别人用着”，而关联关系分两种，处理方式完全相反：

| 关系 | 例子 | 处理 |
|---|---|---|
| **引用** | `outfit_item` 指向衣服 | **禁止删除**，提示先移出搭配 |
| **从属** | `clothing_tag` 属于衣服 | **跟着删**，物理删除 |

**为什么引用不能级联删**：用户在搭配里精心搭好一套衣服，删掉其中一件时如果悄悄把这件从搭配里删掉，用户根本不知道自己的搭配被动过。必须拦下来，让他自己去处理。

**为什么从属必须删**：衣服是逻辑删除（`deleted=1`），记录还在表里。标签不跟着删，`clothing_tag` 里就留下指向“已删除衣服”的孤儿数据，将来做标签统计会算进去，数字虚高。

这个模式直接来自苍穹外卖 `DishServiceImpl.deleteBatch`：

```java
// 第 1 关：状态检查（起售中不让删）
// 第 2 关：引用检查（被套餐关联不让删）
// 两关都过，才真正删 + 清理从属数据（口味）
```

### 四步

1. 查归属，查不到抛异常
2. `outfitItemMapper.selectCount(clothing_id = ?)`，大于 0 就抛 `CLOTHING_IN_USE(2003)`
3. `clothingMapper.deleteById(id)`（`@TableLogic` 自动变成 UPDATE）
4. `clothingTagMapper.delete(clothing_id = ?)`

## 三、批量删除

`DELETE /api/clothing/batch`，body 是 `{ "ids": [3,5,7] }`。

### 四步

1. **判空**：`ids == null || ids.isEmpty()` 直接返回
2. **归属校验**：用 `count` 对比，`selectCount(id IN ids AND user_id = 我)` 的结果必须等于 `ids.size()`，少一个就说明混了别人的 id 或有不存在的 id
3. **引用校验**：`outfitItemMapper.selectCount(clothing_id IN ids)`，大于 0 整批拒绝
4. **批量删**：`clothingMapper.deleteByIds(ids)` + `clothingTagMapper.delete(clothing_id IN ids)`

**归属校验用 count 对比是个很聪明的写法**：不用先查出所有衣服再逐个比对 userId，一条 `COUNT` 就完事。只要数量对不上，就说明这批 id 里不全是自己的。

### 路径必须用固定字面量

```java
@DeleteMapping("/{ids}")   // ✗ 和 @DeleteMapping("/{id}") 冲突
@DeleteMapping("/batch")   // ✓
```

Spring 看来 `/{id}` 和 `/{ids}` 是**同一个路径模式**（都是一个路径段变量），两个方法映射到同一批 URL，启动时直接抛 `Ambiguous mapping`，整个应用起不来。

`/batch` 是字面量，匹配优先级高于变量，不会和 `/{id}` 抢。

## 四、MyBatis-Plus 的 `in` 是什么

对应 SQL 的 `IN` 操作符，意思是“等于其中任意一个”。

**单值用 `eq`，多值用 `in`**：

```java
.eq(Clothing::getId, 3L)          // → WHERE id = 3
.in(Clothing::getId, ids)         // → WHERE id IN (3,5,7)
```

批量删除里用到了三处：

```java
// ① 这批 id 里有几件真属于我
clothingMapper.selectCount(... .in(Clothing::getId, ids) ...)
// SELECT COUNT(*) FROM clothing WHERE id IN (3,5,7) AND user_id = 2

// ② 这批衣服有没有被搭配引用
outfitItemMapper.selectCount(... .in(OutfitItem::getClothingId, ids))
// SELECT COUNT(*) FROM outfit_item WHERE clothing_id IN (3,5,7)

// ③ 删这批衣服的所有标签
clothingTagMapper.delete(... .in(ClothingTag::getClothingId, ids))
// DELETE FROM clothing_tag WHERE clothing_id IN (3,5,7)
```

**为什么不能写成 for 循环**：循环 3 次 = 3 条 SQL + 3 次数据库往返。`in` 一条 SQL 搞定。批量操作的核心就是这个。

**两个坑**：

- 集合不能为空，`IN ()` 是 SQL 语法错误，必须提前判空
- 集合不能太大，几千个 id 拼进 `IN` 会撑爆 SQL 长度，也走不了索引，要分批（每批 500 左右）

反向方法是 `notIn`，用法一样。

## 五、前端调整

**① 两个详情页都补了返回按钮**

`ClothingDetail.vue` 一个组件承担两种角色，靠 `route.meta.readOnly` 区分：

| 从哪进来 | 顶部按钮 | 返回到 |
|---|---|---|
| 我的衣柜 → 点卡片（只读） | 返回衣柜 / 只读 / 去工作台编辑 | `/wardrobe` |
| 衣物管理 → 点卡片（可改） | 返回列表 / 删除 / 编辑 | `/workspace/wardrobe` |

两边跳的方向不同是有意的：浏览态回“我的衣柜”，工作台回“衣物管理”，各回各的上一级。

**② 删掉了「浏览态预览」按钮**

原来工作台点它会跳到只读页，只读页又能点「去工作台编辑」跳回来，形成往返循环。删掉之后链路清爽了。

**③ 详情页标签改成下拉多选**

原本是 `el-tag + el-input` 回车添加，现在和添加页统一成 `el-select multiple filterable allow-create`。

改动涉及 5 处：模板换控件、加 `styleOptions` / `occasionOptions` 候选数组、`styleTags` / `occasionTags` 从 `computed` 改成 `ref([])`、删掉 `addTag` / `removeTag`、`load()` 里拆包 `onSave()` 里拼回。

**最后那一步最容易漏**：下拉框双向绑定的是两个独立数组，提交前必须拼回 `clothing.tags`，否则发出去的还是页面加载时那份旧标签，等于白改。

**④ 列表卡片布局定稿**

试了三轮才定下来：固定 6 列 `repeat(6, 1fr)`。

中间踩的坑值得记：

- `auto-fill` 会创建**没东西的空列**并占位，卡片不满一行时右侧留一大块空白
- `auto-fit` 会折叠空列，但只有一个卡片时会把它拉成整行宽（`1fr` 贪心吃满）
- 给 `minmax` 加第二参数（如 `minmax(150px, 240px)`）能防拉伸，但会产生留白
- **根本矛盾**：容器宽度固定时，“卡片填满整行”和“条数少时卡片更大”只能二选一

最终选固定 6 列：卡片宽度 = 容器宽度 ÷ 6，永远填满，每页条数只决定显示几行。

## 六、踩坑记录

**① `@RequestBody List<Long>` 接不了 `{"ids": [...]}`**

```json
{"ids":[3,5,7]}   →  必须用 BatchDeleteDTO 或 Map 接
[3,5,7]           →  才能用 List<Long> 接
```

前者是对象（有 key），后者是裸数组，Jackson 眼里是两种东西。用错报 `Cannot deserialize from Object value`。

这是最容易搞混的地方：前端 `data: { ids }` 是 ES6 简写，等价 `data: { ids: ids }`，发出去**带一层大括号**。

**② 路径变量冲突**

见第三节。

**③ `::` 是方法引用，不是调用**

`Clothing::getUserId` 读作“Clothing 的 getUserId 方法”，它没有调用，只是**指向**这个方法，把方法本身当值传出去。等价于 `clothing -> clothing.getUserId()`。

MyBatis-Plus 拿它反推列名：`getUserId` → `userId` → `user_id`。

用方法引用而不是字符串的好处是**错误暴露时机**：`Clothing::getUserId` 写错当场标红编译不过，`"user_id"` 写错要等运行时抛 `Unknown column`。

**④ `LambdaQueryWrapper` 是“条件收集器”**

`new` 出来是空的，每调一次 `.eq` / `.like` / `.in` / `.apply` 就往里塞一条，最后交给 mapper 翻译成 SQL。

`eq` 的三参数重载 `eq(boolean condition, 列, 值)` 可以用一个布尔值控制这条条件拼不拼，所以四个可选筛选项不用写 if。
