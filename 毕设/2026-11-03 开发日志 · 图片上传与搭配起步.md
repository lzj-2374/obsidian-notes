## 一、OSS 接入

### 建 Bucket 时三个不可逆的选择

| 选项 | 结论 | 后果 |
|---|---|---|
| 地域 | 华北2（北京） | **建完不能改**，决定 Endpoint 域名 |
| Bucket 名称 | `lzj-wardrobe-ai` | **建完不能改** |
| 读写权限 | **公共读** | 选「私有」图片在浏览器里全是 403，衣柜变成一片空白 |

### 不用配 CORS

网上教程让配跨域，是因为它们做的是**前端直传**（浏览器直接把文件发给 OSS）。

本项目的链路是「浏览器 → Spring Boot → OSS」，图片由后端推上去，浏览器从头到尾没碰过 OSS，所以不存在跨域问题。配了也是白配。

### AccessKey 的两个坑

- `AccessKeySecret` **只在创建成功那一个弹窗显示一次**，关掉就永久看不到，只能删了重建
- 主账号的 AK 权限是**全部云资源**，泄露了别人能删你服务器。正规做法是建 RAM 子账号只授 `AliyunOSSFullAccess`

### 实测三项（绕过 Java，直接用签名 HTTP 验证）

```
PUT 上传        → HTTP 200
匿名 GET 读取    → HTTP 200   （证明「公共读」生效）
DELETE 删除     → HTTP 204
```

先验 OSS 本身通不通，再写代码。这样后面接口报错时，能确定不是云平台的问题。

## 二、依赖与配置

### JDK 17 必须补三个 jaxb 依赖

```xml
<dependency>aliyun-sdk-oss 3.17.4</dependency>
<dependency>javax.xml.bind:jaxb-api 2.3.1</dependency>
<dependency>javax.activation:activation 1.1.1</dependency>
<dependency>org.glassfish.jaxb:jaxb-runtime 2.3.3</dependency>
```

JDK 9 起 `javax.xml.bind` 被移出标准库，而 OSS SDK 内部还在用它解析 XML。不补的话编译能过，**运行期才抛** `NoClassDefFoundError: javax/xml/bind/DatatypeConverter`——报错位置在 SDK 内部，很难联想到是 JDK 版本问题。

### multipart 默认只有 1MB

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 10MB
```

手机随手拍的照片 3~5MB，不调这个一上传就 `MaxUploadSizeExceededException`。

### `${ENV:默认值}` 的写法

```yaml
endpoint: ${OSS_ENDPOINT:oss-cn-beijing.aliyuncs.com}
```

含义是「先读环境变量 `OSS_ENDPOINT`，读不到才用冒号后面的默认值」。

比把密钥硬写在 yml 里再靠 `.gitignore` 强——`.gitignore` 经常漏，而且 yml 是必需文件，没法整个忽略。

## 三、上传接口

### 四步

```
upload(file, bizType)
 ├─ 0. 从 UserContext 拿 userId    谁传的，不接受前端传
 ├─ 1. 校验                        空文件？扩展名白名单？
 ├─ 2. 造 key                      wardrobe/2026/11/03/uuid.jpg
 ├─ 3. 推 OSS                      拿回访问地址
 └─ 4. 插 file 表                  记账
```

### 为什么必须自己生成文件名

原始文件名有三个问题：

| 问题 | 后果 |
|---|---|
| 中文名 | url 变成一长串 `%E6%88%91...`，又长又难读 |
| 重名 | 两个人同时传 `IMG_001.jpg`，后者覆盖前者（手机相册默认就叫这个） |
| 路径穿越 | 文件名里带 `../` 能跑到桶目录外面 |

所以统一 UUID，原名只存 `file_name` 列给人看。

### `url` 和 `oss_key` 必须都存

| 字段 | 长什么样 | 给谁用 |
|---|---|---|
| `url` | `https://lzj-wardrobe-ai.oss-cn-beijing.aliyuncs.com/wardrobe/2026/11/03/x.jpg` | 前端当 `img src` |
| `oss_key` | `wardrobe/2026/11/03/x.jpg` | 后端删文件 |

OSS 的 `deleteObject` **只认 key，不认完整 url**。只存 url、删的时候去字符串截取，是典型的埋雷。

### 必须显式设 Content-Type

```java
metadata.setContentType("image/jpeg");
```

不设的话 OSS 按 `application/octet-stream` 存。浏览器打开这个地址不是显示图片，而是**弹出下载框**。整个衣柜会变成一堆裂图。

### 这里为什么不用事务

整个方法只有**一次** INSERT，事务没有额外保护作用。

真正需要兜底的是「图已经推到 OSS，但表没写成功」——**这种失败事务回滚不了 OSS**，只能手动把刚传上去的对象删掉：

```java
} catch (Exception e) {
    safeDelete(key);   // 补偿删除，删失败只记日志，不能盖住原始错误
    throw new BusinessException(...);
}
```

加事务反而给人「已经安全了」的错觉。

## 四、脏数据：`blob:` 地址的坑

### 现象

OSS 控制台「暂无数据」，但衣柜里有一件衣服显示了图片，数据库里 `image_url` 是：

```
blob:http://localhost:5173/b0764698-c0f8-4c16-b362-33f2f5514565
```

### 原因

`ClothingAdd.vue` 的 `el-upload` 是 `:auto-upload="false"`，这意味着**组件自己不会调上传接口**，只把文件交给 `on-change` 回调。而回调里只做了：

```js
previewUrl.value = URL.createObjectURL(uploadFile.raw)
```

`createObjectURL` 生成的是**浏览器内存地址**，只活在当前标签页，刷新就废，更不可能传到 OSS。提交时又把这个 blob 地址当图片地址存进了数据库。

`uploadFile` 这个函数在文件顶部 import 了，但**全文件没有任何地方调用过**。

### 修法

把「预览地址」和「真实地址」分成两个变量：

| 变量 | 用途 | 能不能进数据库 |
|---|---|---|
| `previewUrl` | `<el-image :src>` 显示 | **永远不能** |
| `imageUrl` | 提交给后端 | 只有它进库 |

上传时机选「提交时才传」而不是「选图就传」，避开「图还在传用户就点了保存」的竞态。关键是 `await`——不 await 的话代码直接往下跑，`payload` 拿到空字符串。

### 清理

```sql
UPDATE clothing SET image_url = NULL WHERE image_url LIKE 'blob:%' OR image_url = '';
```

清掉了 6 行。

## 五、搭配分页：N+1 问题

### 问题

`outfit` 表里没有「单品数量」这一列，`items` 在 `outfit_item`。如果写成「查 20 条搭配 → for 循环给每条查一次 items」，就是 **21 次 SQL**。

### 解法：两次 SQL

```
第 1 次：分页查 outfit                → 20 条，id 是 [11,12,13...]
第 2 次：in + 这堆 id 查 outfit_item  → 一次捞回所有单品
然后：内存里按 outfitId 分组，塞回去
```

分组用：

```java
Map<Long, List<OutfitItem>> grouped = allItems.stream()
        .collect(Collectors.groupingBy(OutfitItem::getOutfitId));
```

`groupingBy` 就是「按某个字段把一堆对象分堆」，`OutfitItem::getOutfitId` 是分堆依据。

### `items` 放实体还是新建 VO

选了**实体 + `@TableField(exist = false)`**：

```java
@TableField(exist = false)
private List<OutfitItem> items;
```

理由是跟 `Clothing.tags` 保持一致。`exist = false` 告诉 MyBatis-Plus：查表和 INSERT 时都当这个字段不存在，它只在内存里用来捎带数据。所以新增/修改接口不会因为多这个字段报 `Unknown column`。

### 空列表 vs null

```java
outfit.setItems(grouped.getOrDefault(outfit.getId(), new ArrayList<>()));
```

前端 `items?.length` 遇 null 显示 0 没问题，但以后写 `for (item : outfit.getItems())` 时 null 直接 NPE。统一给空列表。

## 六、新建搭配

### 四步

```
add(dto)
 ├─ 1. 校验        name 非空？items 非空？role 1~5 且不重复？
 ├─ 2. 归属校验   这些 clothingId 是不是你的衣服
 ├─ 3. 插主表     insert 后 getId() 自动回填
 └─ 4. 挂 items   用这个 id 逐条 insert
```

### 必须加事务（跟文件上传正好相反）

| | 文件上传 | 新建搭配 |
|---|---|---|
| 写几张表 | 1 张 | 2 张 |
| 事务 | 没必要 | **必需** |

不加会怎样：主表插成功、第 3 条 item 撞唯一索引报错，**主表那条已经提交了**——数据库里多出一条没有任何单品的搭配，列表页上是一张「0 件单品」的幽灵卡片。

### `Set` 去重的真正原因

不是为了少查几条，而是因为**同一件衣服可以同时占两个角色**（一件卫衣既算上装又算外套）。用 `List` 收集就是 `[7, 7]`，size=2；数据库 `count` 出来是 1，永远对不上，用户会被误判成「包含无效衣物」。

### `source` 不能采信前端

前端新建时确实传了 `"source": 1`，但后端**硬编码写 1**。

`source=2`（AI 推荐沉淀）只允许 AI 模块那条路径写。接了前端传值，就能有人用 Postman 伪造「AI 推荐搭配」，管理端的「搭配来源分布」统计直接失真。

### 插入时一定要 `new` 一个新对象

```java
for (OutfitItem src : dto.getItems()) {
    OutfitItem item = new OutfitItem();   // 不能直接插 src
    ...
}
```

`dto.items` 里的是前端 JSON 反序列化来的对象，可能带 `id` 或 `outfitId`。直接插轻则主键冲突，重则把单品挂到**别人的搭配**上。

## 七、搭配详情：一口气踩了六个坑

这段是今天最有价值的部分，因为每个错误都很典型。

### ① 返回类型写成 `void`

```java
void detail(Long id);          // 接口
public void detail(Long id) {  // 实现
    return outfit;             // 编译不过
}
```

`void` 和 `return 值` 互相矛盾。而且这会导致**数据从源头就断在 Impl 里**——接口不返回数据，Controller 只能 `Result.ok()` 返回个空壳。

### ② Controller 路径漏了 `{id}`

```java
@GetMapping                    // ✗
public Result<Outfit> detail(@PathVariable Long id)
```

`@PathVariable` 的意思是「从**路径**里抠出一个变量叫 id」，但路径里根本没有这个变量。运行时抛：

```
Missing URI template variable 'id'
```

必须写 `@GetMapping("/{id}")`。

### ③ `Result.ok()` 把数据扔了

```java
outfitService.detail(id);      // 返回值没人接
return Result.ok();            // 无参版本，data 是 null
```

Java 允许忽略返回值，所以**编译不报错**，但前端拿到的永远是 null。

### ④ 用 `selectOne` 查从表

```java
outfitItemMapper.selectOne(...eq(outfitId, id));
```

一个搭配有 4 件单品就是 4 行，`selectOne` 查到多条会抛 `TooManyResultsException`。**只要搭配里超过一件衣服，这个接口 100% 崩。** 必须用 `selectList`。

### ⑤ 查出来的 items 没塞回 outfit

```java
outfitItemMapper.selectList(...);   // 查了，然后扔了
return outfit;                       // items 还是 null
```

这个最坑：**接口返回 HTTP 200，控制台无异常**，但 `data.items` 是 null。前端 `(res.items || [])` 得到空数组，编辑页 5 个格子一件衣服都没有，用户只会觉得「我的搭配怎么空了」。

比 500 难查十倍，因为所有监控都显示正常。

### ⑥ 错误码语义错

查不到搭配用了 `OUTFIT_ITEM_INVALID(3003)`「搭配中包含无效衣物」，应该是 `OUTFIT_NOT_FOUND(3001)`。

错误码不只是给前端看的，答辩时被问「你这个 3003 是什么场景」，答不上来很尴尬。

### 顺带：不要区分「不存在」和「不是你的」

```java
selectOne(id = ? and user_id = ?)
   ↓ null
抛 OUTFIT_NOT_FOUND（不管是不存在还是别人的）
```

如果区分了，别人能拿 id 从 1 试到 10000，通过报错差异把「哪些 id 真实存在」全摸出来。这跟登录时不说「用户不存在」、只说「用户名或密码错误」是同一个道理，叫**资源枚举**。

## 八、零散踩坑

### ① `@service` 全小写

注解名大小写敏感，`@Service` 才对。小写直接编译不过。

### ② `items == null` 的 NPE

`OutfitDTO` 里的 `items` 没有初始化默认值，前端**不传这个字段时反序列化出来是 null**，不是空列表。`null.isEmpty()` 直接 NPE，用户看到「服务器异常」而不是「请至少选择一件单品」。

必须先判 null 再判 isEmpty。

### ③ `isEmpty()` vs `isBlank()`

`isEmpty` 只判长度 0，**纯空格能通过**。用户输三个空格能存进去，列表上就是一个看不见名字的卡片。

### ④ Apifox 里 `password: 123456` 报 400

数字没有引号，而 `LoginDTO.password` 是 `String`。Jackson 在严格配置下抛 `HttpMessageNotReadableException`，Spring 回一个默认错误页——**请求根本没进方法**，所以既没有业务日志也没有你的 `Result` 结构。

判断依据：响应长 `{timestamp,status,error,path}` 这样而不是 `{code,message,data}`，就说明是框架层拒绝的，不是业务异常。

### ⑤ `GlobalExceptionHandler` 缺兜底（待修）

现在只写了 `@ExceptionHandler(BusinessException.class)`。其他异常（参数解析失败、NPE、SQL 报错）全走 Spring 默认错误页，**返回里没有 `code` 字段**。

而前端 axios 拦截器读的是 `code` 来决定跳登录页还是弹提示——拿不到 `code` 就只能静默失败，用户只看到「网络异常」。

要补：

```java
@ExceptionHandler(Exception.class)
// 里面 log.error 打堆栈 + 返回 Result.fail(500, "服务器异常")
```

### 删除搭配的要点

主表逻辑删除（`@TableLogic` 自动变 UPDATE），从表物理删除。两张表删除方式不同，跟衣柜删除单件是同一个模式。
