## 一、衣柜分页查询

`GET /api/clothing/page?page=1&size=6&category=1&keyword=衬衫&season=1`

参数全走 query，所以用 `@RequestParam`，三个可选项必须 `required = false`，否则前端不传就是 400。

### 三层各自的活

**Controller** 只做转手，不碰任何条件判断：

```java
return Result.ok(clothingService.pageQuery(page, size, category, keyword, season));
```

**Service 接口** 的方法签名里**故意没有 userId**，身份由实现类从 `UserContext` 取。这样 Controller 结构上就没机会把别人的 id 传进来。

**ServiceImpl** 四步：

```java
Long userId = UserContext.getUserId();
Page<Clothing> clothingPage = new Page<>(page, size);
LambdaQueryWrapper<Clothing> wrapper = new LambdaQueryWrapper<>();
wrapper.eq(Clothing::getUserId, userId);
wrapper.eq(category != null, Clothing::getCategory, category);
wrapper.like(StringUtils.hasText(keyword), Clothing::getName, keyword);
wrapper.apply(season != null, "season & {0} > 0", season);
wrapper.orderByDesc(Clothing::getCreateTime);
return clothingMapper.selectPage(clothingPage, wrapper);
```

### 三个关键点

**① `eq` 的三参数重载是 MyBatis-Plus 的省心设计**

`eq(boolean condition, 列, 值)` —— 第一个参数为 true 才拼这段 SQL，false 就跳过。所以四个可选筛选项全都不用写 `if`，一行一个。

**② `season` 必须用位运算，不能用等号**

季节存的是位标识：1 春 / 2 夏 / 4 秋 / 8 冬，相加即组合。一件春夏季的衣服存的是 `3`，四季通用的存 `15`。

如果写成 `eq(Clothing::getSeason, 1)`，`3` 和 `15` 都查不出来。正确写法是：

```java
wrapper.apply(season != null, "season & {0} > 0", season)
```

`{0}` 是 MyBatis-Plus 的占位符，会安全替换成参数值，不要用字符串拼接。

> [!tip] 怎么验证位运算真的生效
> 数据里必须有两件**只属于单一季节**的衣服（比如 `season=2` 的短袖、`season=8` 的羽绒服），否则所有数据都包含"春"，筛完数量不变，看不出效果。

**③ 必须补排序**

`wrapper.orderByDesc(Clothing::getCreateTime)`。不加的话 MySQL 不保证返回顺序，翻页时同一条数据可能重复出现在两页里。

### 返回整个 Page，不是 getRecords()

前端 `Wardrobe.vue:121` 读的是 `res.records` 和 `res.total`。`Page` 对象序列化后自带 `records / total / size / current / pages` 五个字段，直接 `return clothingMapper.selectPage(...)` 就行。

对比黑马点评：那边只 `return page.getRecords()`，因为它前端是无限滚动，不需要总数。

## 二、衣柜详情

`GET /api/clothing/{id}` → 一件衣服 + 它的所有标签。

### 为什么不能直接用 selectById

```java
clothingMapper.selectById(id)   // ✗ 只按主键查，谁都能看
```

地址栏把 `/clothing/5` 改成 `6`，就能翻到别人的衣服。必须两个条件：

```java
clothingMapper.selectOne(new LambdaQueryWrapper<Clothing>()
        .eq(Clothing::getId, id)
        .eq(Clothing::getUserId, UserContext.getUserId()));
```

查出来是 null 就抛 `CLOTHING_NOT_FOUND(2001)`，对外表现为"衣物不存在"，不暴露"存在但不属于你"。

### 标签在另一张表，需要查两次

```java
List<ClothingTag> tags = clothingTagMapper.selectList(
        new LambdaQueryWrapper<ClothingTag>().eq(ClothingTag::getClothingId, id));
clothing.setTags(tags);
```

`selectList` 不是 `selectOne` —— 一件衣服有多个标签，`selectOne` 遇到两条直接抛 `TooManyResultsException`。

第二次查询**不用再带 userId**，第一次已经校验过归属了，标签表也没有 userId 列。

### `@TableField(exist = false)`

`Clothing` 实体上加了一个虚拟字段：

```java
@TableField(exist = false)
private List<ClothingTag> tags;
```

不加这个注解，`selectById` / `selectPage` 生成的 SQL 会带上 `tags` 列，MySQL 报 `Unknown column 'tags'`，列表页直接 500。

加了之后：SQL 里不出现这一列，但 Java 对象里字段还在，能手动 `set`，转 JSON 时也照常输出。

> [!important] 判断标准
> 返回的东西还是数据表里那一行（哪怕带了几个关联字段），就直接用实体 + `exist = false`。
> 如果是算出来的、拼出来的、代表一个全新概念（比如 `OverviewVO` 的衣物数、`LoginVO` 的 token+user），才建 VO。

### `clothing_tag` 为什么单独一张表

一件衣服可以有多个风格、多个场合，放主表存不下；存成 `"简约,通勤"` 又没法查——找"所有通勤的衣服"只能 `LIKE '%通勤%'`，既慢又会误匹配。

拆成独立表，一行一个标签：

| 列 | 含义 |
|---|---|
| `id` | 主键 |
| `clothing_id` | 属于哪件衣服 |
| `tag_type` | 1 风格 / 2 场合 / 3 其他 |
| `tag_value` | 具体值 |

这是典型的**一对多**。这张表不做逻辑删除，编辑时走"先按 `clothing_id` 全删、再整批插入"，物理删除。

## 三、衣柜新增

`POST /api/clothing` → 一次写两张表。

### 为什么要建 ClothingDTO

`Clothing` 实体没有 `tags` 字段的入参形态（虽然加了虚拟字段，但语义上是查询结果），而且直接拿实体当入参等于把 `userId`、`status`、`deleted` 全暴露给前端。

`ClothingDTO` 只放前端真正要传的八个字段：`name / category / subCategory / color / season / thickness / imageUrl / tags`。

**故意不放**：`id`（自增）、`userId`（从 token 取）、`status`（服务端定）、`createTime / updateTime`（数据库填）、`deleted`（逻辑删除标记）。

### 实现三步

```java
@Transactional
public void add(ClothingDTO dto) {
    Long userId = UserContext.getUserId();

    Clothing clothing = new Clothing();
    BeanUtils.copyProperties(dto, clothing);
    clothing.setUserId(userId);
    clothing.setStatus(EnableStatus.ENABLED.getCode());
    clothingMapper.insert(clothing);          // ← 这一步之后 id 才有值

    for (ClothingTag tag : dto.getTags()) {
        tag.setClothingId(clothing.getId());
        clothingTagMapper.insert(tag);
    }
}
```

### 三个关键点

**① 自增主键会自动回填**

实体上标的是 `@TableId(type = IdType.AUTO)`，`insert` 执行完，MyBatis-Plus 会把数据库生成的 id **写回 `clothing.getId()`**。不用再查一次，也不用 `SELECT LAST_INSERT_ID()`。

这也是为什么 `insert` 必须写在 `for` 循环之前——标签要拿这个 id 才知道挂在哪件衣服上。

**② `@Transactional` 不能省**

插衣服成功、插标签时数据库出问题，没有事务会留下一件没标签的半残衣服。加了之后要么全成功，要么全回滚。

**③ 用 `setUserId`，不是 `setId`**

```java
clothing.setId(userId);        // ✗ 把 userId 当主键了
clothing.setUserId(userId);    // ✓
```

写成 `setId` 的后果不只是主键冲突：`clothing.getId()` 会返回 userId，标签就挂到 id 等于 userId 的那件衣服下面，可能挂到别人的衣服上。

## 四、状态码统一成 EnableStatus

原本两张表的 status 语义是**反的**：

```sql
-- user 表
status TINYINT NOT NULL DEFAULT 1 COMMENT '1 正常 / 0 停用'
-- clothing 表（改造前）
status TINYINT NOT NULL DEFAULT 0 COMMENT '0 正常 / 1 已归档'
```

如果各自建一个枚举，复制代码时很容易搞混，而且混了不报错，只是业务判断全反。

统一成「1 正常 / 0 停用」之后共用一个枚举：

```java
public enum EnableStatus {
    ENABLED(1, "正常"),
    DISABLED(0, "停用");
}
```

**已经建好的库要手动改**（`init.sql` 改的是新建库的时候生效）：

```sql
ALTER TABLE clothing MODIFY COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '1 正常 / 0 已归档';
UPDATE clothing SET status = 1;
```

用法：`clothing.setStatus(EnableStatus.ENABLED.getCode())`。

**不能直接把枚举塞进去**，`setStatus` 要的是 `Integer`，Java 不会自动帮你拆，必须 `.getCode()`。

> [!note] status 和 deleted 不是一回事
> `deleted` 是逻辑删除（用户主动删掉了），`status` 是业务状态（记录还在，只是暂时不用）。列表查询目前只自动过滤 `deleted`，没过滤 `status`，归档的衣服照样显示。

## 五、踩坑记录

**① `Page<Object>` 泛型不匹配**

```java
Page<Object> objectPage = new Page<>(page, size);
return clothingMapper.selectPage(objectPage, wrapper);   // 编译报错
```

`selectPage` 的签名是 `<P extends IPage<T>> P selectPage(P page, Wrapper<T> wrapper)`，编译器从 wrapper 推出 `T = Clothing`，要求 `Page<Object>` 是 `IPage<Clothing>`，不成立。

Java 泛型不支持协变，`Page<Object>` 和 `Page<Clothing>` 之间没有继承关系。

**② 括号位置错，方法链挂到了错误的对象上**

```java
clothingMapper.selectOne(new LambdaQueryWrapper<Clothing>()
        .eq(Clothing::getId, id))        // ← 两个右括号，把 selectOne 提前关了
        .eq(Clothing::getUserId, userId); // ← 这个 eq 挂到了 Clothing 上
```

`selectOne` 返回 `Clothing`，`Clothing` 没有 `eq` 方法。正确姿势是最后才关 `selectOne` 的括号。

**③ POST 接口漏了 `@RequestBody`**

漏了不会报"缺注解"，而是所有字段都变成 null，插入时数据库报 `Column 'name' cannot be null`，然后去怀疑前端没传数据、字段名拼错，绕很久。

三个注解的对应关系：

| 数据位置 | 注解 |
|---|---|
| JSON 请求体 | `@RequestBody` |
| URL 问号后面 | `@RequestParam` |
| 路径里 `/clothing/5` | `@PathVariable` |

**④ `void` 方法不能当参数用**

```java
return Result.ok(clothingService.add(dto));   // ✗ add 返回 void
```

拆成两行：先调，再 `return Result.ok()`。

**⑤ 前端 computed 不能 v-model**

衣物详情页原本的标签用 `computed` 从 `clothing.tags` 算出来，是只读派生值，绑不上下拉框。要改成 `ref([])`，并在 `load` 里拆包、`onSave` 里拼回去。

漏了 `onSave` 那一步，界面上标签改了但 `clothing.tags` 没变，保存等于没改。

## 六、下一步

衣柜还剩三个接口：

| 接口 | 说明 |
|---|---|
| `PUT /clothing/{id}` | 修改，id 用路径里的，body 里的 id 一律忽略 |
| `DELETE /clothing/{id}` | 单条删除，`@TableLogic` 自动变 UPDATE |
| `DELETE /clothing/batch` | 批量，body 是 `{ids: [...]}`，DELETE 带 body 容易踩坑 |

`PUT` 的实现要点和新增几乎一样，区别是：

- 用 `updateById` 之前要先校验归属（`id + user_id` 查一次）
- 标签更新用**先删后插**：按 `clothing_id` 删干净，再把新的插进去
- `updateById` 只更新非 null 字段，前端传 null 的字段不会变动

批量删除要多做两件事：过滤掉不属于当前用户的 id，顺手清掉 `outfit_item` 里引用这些衣服的记录（那张表没有外键约束，不清就会在搭配里留下空白格子），整段加 `@Transactional`。
