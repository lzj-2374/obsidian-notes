## 1. Spring Task 定时任务

Spring Task 是 Spring 框架提供的任务调度工具，可以**按约定时间自动执行**某段代码逻辑。

- **定位**：定时任务框架
- **作用**：定时自动执行某段 Java 代码
- **应用场景**：
  - 信用卡每月还款提醒
  - 银行贷款每月还款提醒
  - 火车票售票系统处理未支付订单
  - 入职纪念日为用户发送通知

### 1.1 cron 表达式

cron 表达式是一个**字符串**，通过它定义任务触发的时间。

**构成规则**：分为 6 个或 7 个域（写年就是 7 域，不写就是 6 域），用空格隔开：

| 域（顺序） | 含义 | 取值范围 |
|---|---|---|
| 1 | 秒 | 0-59 |
| 2 | 分钟 | 0-59 |
| 3 | 小时 | 0-23 |
| 4 | 日（day of month） | 1-31 |
| 5 | 月 | 1-12（或 JAN-DEC） |
| 6 | 周（day of week） | 1-7，或 SUN MON TUE WED THU FRI SAT |
| 7 | 年（可选） | 1970-2099 |

**常用符号**：

| 符号 | 含义 | 示例 |
|---|---|---|
| `*` | 匹配所有值 | 分钟域 `*` = 每分钟 |
| `,` | 枚举 | `9,12,15` = 9 点、12 点、15 点 |
| `-` | 范围 | `10-12` = 10 点到 12 点 |
| `/` | 步长 | `0/15` = 从 0 开始每隔 15 |
| `?` | 不限制该域（"不确定值"） | **仅用于"日"和"周"两个域** |
| `L` | 最后 | 日域：每月最后一天；周域：最后某天 |
| `W` | 最近工作日 | `15W` = 15 号那天最近的一个工作日 |

**常用示例**：

| 表达式 | 含义 |
|---|---|
| `0 * * * * ?` | 每分钟执行一次 |
| `0 0 1 * * ?` | 每天凌晨 1 点执行 |
| `0 0 1 ? * MON` | 每周一 1 点执行 |
| `0 0 1 1 10 ? 2026` | 2026 年 10 月 1 日 1 点执行一次 |
| `0 0 1 ? 10 MON 2026` | 2026 年 10 月每个周一 1 点执行 |

一般不手写，用在线生成器：`https://cron.qqe2.com/`

#### 📌 "日"和"周"为什么不能同时指定？（`?` 规则详解）

这是 Quartz 风格 cron（Spring Task 用的就是它）的一条硬性规则：**"日"和"周"两个域中，必须有一个是 `?`**。

1. **为什么**：
   - "日"和"周"本质都在限制"这个月的哪一天"——"日"按**日期**（1–31）限制，"周"按**星期**（MON–SUN）限制，两个维度是**重叠**的（任何一天既是某月某号，也是某星期几）。
   - 如果两个都指定，语义就**有歧义**了：
     - 按**交集**（AND）理解：只有"1 号 且 是周一"才执行——而 10 月 1 号不一定是周一，任务可能永远不触发；
     - 按**并集**（OR）理解："每月 1 号"和"每周一"都执行。
     - 标准 Unix cron 是取并集，Quartz 干脆**不允许两个同时写具体值**，从语法层面避免歧义。
2. **怎么办**：想限制哪个维度，另一个就写 `?`（含义 = "该维度不限制"）：
   - 按"月里的某号"限制 → 周日 = `?`。例：2026 年 10 月 1 日 1 点执行一次：`0 0 1 1 10 ? 2026`；
   - 按"星期几"限制 → 日域 = `?`。例：2026 年 10 月每个周一 1 点执行：`0 0 1 ? 10 MON 2026`。
3. **`?` 与 `*` 的区别**：
   - 作用相同，都是"不关心这个域"；但 `?` **只能用在"日"和"周"**；
   - `?` 是强制约定：写 Quartz cron 时 `* * * * * * *`（全星号）是**不允许**的，日/周必须有一个是 `?`，逼你明确"这次到底按哪一天维度调度"。

### 1.2 Spring Task 使用步骤

1. 导入 Maven 坐标 `spring-context`（`spring-boot-starter` 下已存在，无需单独引入）
2. 启动类添加 `@EnableScheduling` 开启任务调度
3. 自定义定时任务类，在任务方法上加 `@Scheduled(cron = "表达式")`

```java
@Component
public class OrderTask {

    // 每分钟执行一次
    @Scheduled(cron = "0 * * * * ?")
    public void taskA() { ... }

    // 每天凌晨 1 点执行一次
    @Scheduled(cron = "0 0 1 * * ?")
    public void taskB() { ... }
}
```

### 1.3 苍穹外卖中的定时任务场景

如果用户下单后一直未支付，或者收货后管理端一直没点"完成"，订单会一直卡在"派送中"，不合理，可以用定时任务处理：

- **一直未支付**：定时任务**每分钟**检查一次，是否存在支付超时订单（下单后超过 15 分钟未支付），存在则把订单状态改为"已取消"；
- **一直"派送中"**：每分钟检查一次显然不合理，改为**每天固定时间点**（如凌晨 1 点）检查一次，存在则改为"已完成"。

示例骨架：

```java
@Component
public class OrderTask {

    @Resource
    private OrderService orderService;

    // 每分钟：下单超过 15 分钟未支付的订单 → 已取消
    @Scheduled(cron = "0 * * * * ?")
    public void cancelTimeoutOrder() {
        // 查未支付且下单时间早于 (now - 15min) 的订单，改为"已取消"
    }

    // 每天凌晨 1 点：仍停留在"派送中"的订单 → 已完成
    @Scheduled(cron = "0 0 1 * * ?")
    public void finishPendingOrder() {
        // 把 status = 派送中 的订单批量改为"已完成"
    }
}
```

## 2. WebSocket

WebSocket 是基于 **TCP** 的一种新的网络协议，实现了浏览器与服务器**全双工**通信——浏览器和服务器只需要完成**一次握手**，两者之间就可以创建**持久性**连接，并进行**双向**数据传输。

### 2.1 HTTP 与 WebSocket 对比

| 对比项 | HTTP | WebSocket |
|---|---|---|
| 连接 | **短连接**，每次请求都要重新建立 | **长连接**，握手一次后连接保持 |
| 通信方向 | **单向**，基于请求-响应模式（客户端发起） | **双向（全双工）**，服务端可主动推送 |
| 交互模式 | 客户端请求 → 服务器响应，不能主动 | 双方任意时刻都能发数据 |
| 底层 | TCP | TCP |

> [!tip] 核心差异
> HTTP 是"请求驱动"，服务端不能主动发起；WebSocket 是"事件驱动"，服务端可随时主动推送。两者底层都是 TCP 连接。

**应用场景**：弹幕聊天、网页聊天、体育实况更新、股票基金报价实时更新（共同点：服务器数据频繁变化、需要实时推给客户端，用 HTTP 轮询成本高）。

## 3. 管理端来电提醒（基于 WebSocket）

### 3.1 需求分析与设计

- 通过 WebSocket 实现**管理端页面**和**服务端**保持长连接状态；
- 当客户支付后，调用 WebSocket 的相关 API，实现**服务端向客户端推送消息**；
- 客户端浏览器解析服务端推送的消息，判断是**来单提醒**还是**客户催单**，进行相应的消息提醒和语音播报；
- 约定服务端发送给客户端浏览器的数据格式为 **JSON**，字段包括：

| 字段 | 说明 |
|---|---|
| `type` | 消息类型：`1` = 来单提醒，`2` = 客户催单 |
| `orderId` | 订单 id |
| `content` | 消息内容 |

### 3.2 实现要点

- 在 `OrderServiceImpl` 中注入 `WebSocketService`；
- 在"**支付成功，修改订单状态**"（`paySuccess`）方法里添加推送消息功能：先把 JSON 数据封装成一个 Map，再调用 WebSocket API 推送给管理端。

### 3.3 小提示（Nginx 反向代理）

> [!tip] 为什么 `ws://localhost/ws/xxx` 不是 8080 端口也能连上？
> 运行后请求路径为 `ws://localhost/ws/xxxx`（走 80 端口），之所以还能连接成功，是因为 Nginx 的**反向代理**：请求先到达 Nginx，再由 Nginx 转发到后端 8080 服务——前提是 Nginx 里已经配置好了这个路径。

## 4. 今日重点

> [!star] 重点回顾
>
> 1. **Spring Task**：`spring-context` + 启动类 `@EnableScheduling` + 任务方法 `@Scheduled(cron)`。苍穹外卖用它处理两类脏状态：每分钟取消"下单超 15 分钟未支付"的订单；每天凌晨 1 点把长期"派送中"的订单改为"已完成"。
> 2. **cron 表达式**：6/7 个域（秒 分 时 日 月 周 [年]）；常用符号 `*` `,` `-` `/` `?`；**日和周不能同时指定，另一个必须写 `?`**（避免"按日期还是按星期"的语义歧义）。
> 3. **WebSocket vs HTTP**：HTTP 短连接、单向请求-响应；WebSocket 长连接、全双工、服务端可主动推送；底层都是 TCP。
> 4. **来电提醒**：管理端与服务端保持 WebSocket 长连接；客户支付成功后，在 `paySuccess` 里推送 JSON（`type` / `orderId` / `content`），前端解析做消息提醒 + 语音播报。
> 5. **Nginx 支持 ws**：`ws://localhost/ws/xxx` 能连通靠的是 Nginx 反向代理转发到 8080。

## 5. 面试问题

> [!question] 🎤 面试题
> **问题**：说下 cron 表达式的结构？为什么 Quartz 风格 cron 中"日"和"周"不能同时指定？除了 Spring Task 的 `@Scheduled`，项目中还有哪些实现定时任务的方式？

**参考答案**：

1. **结构**：cron 表达式是定义任务触发时间的字符串，由 6 或 7 个域组成：**秒、分、时、日、月、周、（年，可选）**，空格分隔；支持 `*`（任意）、`,`（枚举）、`-`（范围）、`/`（步长）、`?`（不限制，仅限日/周）等符号。
2. **日/周不能同时指定**：
   - 两者都在限制"这个月的哪一天"，维度重叠；同时写具体值会导致语义歧义（交集还是并集？不同实现默认行为不同）；
   - Quartz 的解法：强制其中一个域为 `?`（"该维度不限制"），逼你明确按"月里的某号"还是"星期几"调度；
   - 例：10 月 1 日执行 → `0 0 1 1 10 ?`；10 月每个周一执行 → `0 0 1 ? 10 MON`。
3. **其他定时任务方案**：
   - **Spring Task `@Scheduled`**：轻量、进程内，适合简单定时逻辑（本项目用的就是它）；
   - **Quartz**：更强大的 cron 调度框架，支持持久化（任务存 DB）、集群；
   - **XXL-Job**：分布式任务调度中心，可视化配置、失败重试、分片执行，适合多实例部署防止任务重复执行；
   - **延迟队列 / 时间轮**（Redis ZSet、RabbitMQ 延迟消息、Kafka）：适合"精确延迟"场景，比如"下单 15 分钟未支付就取消"——用延迟消息比每分钟轮询更精准、更省资源，但实现成本更高，本项目用 Spring Task 轮询更简单直接。
