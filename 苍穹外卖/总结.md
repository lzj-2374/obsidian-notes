**Q1.2** 项目为什么拆成三个 Maven 模块？不拆行不行？

> 【考察点】模块化思维、依赖管理
> 【答题框架】common/pojo/server 各自的复用范围 → 拆的好处（复用、依赖清晰、编译快、防止 pojo 依赖 web 层）

**我的回答：** 这个暂时不知道

> ✅ **参考答案**：
> 三个模块职责不同，依赖是单向的：
> - **sky-common**：与业务无关的通用能力——常量（MessageConstant/StatusConstant）、工具类（HttpClientUtil/OSS 工具）、自定义异常、BaseContext、枚举、自定义注解。它不依赖任何业务模块。

> 不拆也能跑（一个模块也能实现全部功能），但耦合高、复用差、编译慢。

**Q1.3** DTO、VO、Entity 三者的区别？为什么不用一个类走到底？

> 【考察点】分层设计意识（这是你项目里高频出现的东西）
> 【答题框架】各自的数据来源和去向 → 混用会有什么问题（暴露不该暴露的字段、密码泄露、数据库结构变化冲击接口）

**我的回答：** DTO是返回给前端的，VO是从前端传过来的，Entity不太清楚，如果用一个类走到底，里面可能出现某个前端只需要返回两个参数，但是类里面可能有十几个参数，出现脏数据，影响速度和内存。

> ⚠️ **修正：你把 DTO 和 VO 说反了。**
>
> ✅ **参考答案**：
> - **DTO（Data Transfer Object）**：**前端 → 后端**，用来接收参数。如 `EmployeeLoginDTO`、`OrdersSubmitDTO`、`OrdersPageQueryDTO`。
> - **VO（View Object）**：**后端 → 前端**，用来返回给页面展示。如 `OrderVO`、`DishVO`、`TurnoverReportVO`。
> - **Entity**：和**数据库表一一对应**的对象。如 `Dish`、`Orders`、`Employee`，字段就是表里的字段。
>
> 记法：**DTO 是"进去的"，VO 是"出来的"，Entity 是"存库的"**。
>
> 为什么不用一个类走到底：
> ① **安全**——直接返回 Entity，`employee` 表的 `password` 字段会一起返回给前端，等于把密码泄露出去；
> ② **解耦**——数据库加个字段，接口返回结构就变了，前端被动受影响；
> ③ **防篡改**——前端多传的字段会直接被写进库（比如前端传个 `status` 就能改订单状态）；
> ④ 可读性差，字段冗余。
>
> 你说的"脏数据、影响内存"方向沾边，但**核心是安全和分层解耦，性能是次要的**。

**Q1.4** 前后端是怎么约定交互的？

> 【考察点】接口设计意识
> 【答题框架】Result 三段式结构（code/msg/data）→ 分页用 PageResult（total + list）→ 日期格式、错误码约定

**我的回答：** 前端通过返回状态码（200，404，500等），不太熟

> ✅ **参考答案**：
> ① **统一响应体** `Result<T>`：`{ code, msg, data }`。本项目约定 `code=1` 成功、`code=0` 失败，`msg` 放提示语，`data` 放业务数据。前端只需要判断 `code`。
> ② **分页统一** `PageResult`：`{ total, records }`，`total` 给前端画分页条，`records` 是当前页数据。
> ③ **鉴权**：B 端请求头带 `token`，C 端带 `authentication`（两端约定不同）。
> ④ **日期格式**：统一 `yyyy-MM-dd`，用 `@DateTimeFormat`（接参）/ `@JsonFormat`（返回）转换。
>
> 补充一个容易踩的对比：本项目把 HTTP 状态码固定成 200，业务错误靠 `code` 表达；更符合 REST 规范的做法是用 HTTP 状态码本身（200/400/401/403/404/500）区分语义。

### 第 2 轮 · 基础实现（10 题）

**Q2.1** MyBatis 的 `#{}` 和 `${}` 有什么区别？你项目里哪里用了 `${}`？

> 【考察点】SQL 注入意识（高频！）
> 【答题框架】预编译 vs 字符串拼接 → `${}` 的风险 → 你项目里订单搜索的 `order by ${orderBy}` 就是隐患，怎么防？（白名单）

**我的回答：** 不知道

> ✅ **参考答案**：
> - `#{}`：**预编译占位符**，MyBatis 生成 `?`，底层用 `PreparedStatement`，参数作为**值**传入，不会被数据库当作 SQL 语法解析 → **天然防 SQL 注入**。
> - `${}`：**字符串直接拼接**进 SQL。如果参数来自用户输入，就能拼出恶意语句 → **有注入风险**。
>
> 项目里用 `${}` 的地方：订单搜索的排序 `order by ${orderBy} desc`。用 `${}` 是因为**列名不能用 `?` 占位**（`order by ?` 会被当成常量字符串，排序失效）。
>
> 怎么防？**白名单校验**——orderBy 只允许是 `order_time`、`amount`、`id` 这几个固定值之一，其他一律拒绝。绝不能把用户输入直接拼进去。

**Q2.2** 分页查询是怎么实现的？PageHelper 的原理是什么？

> 【考察点】是否只会用不会想
> 【答题框架】`PageHelper.startPage` → 拦截器改写 SQL 加 limit → `Page` 对象里为什么有 total → 为什么必须紧跟着执行查询

**我的回答：** MyBatis里面封装了分页插件PageHelper，实现原理不会

> ✅ **参考答案**：
> 用法：`PageHelper.startPage(pageNum, pageSize);` 紧接着执行查询，返回的 `Page<T>` 里有 `total`。
>
> 原理（三步）：
> ① `startPage()` 把分页参数塞进 **ThreadLocal**（`Page` 对象），并不立即生效；
> ② PageHelper 实现的是 MyBatis 的 `Interceptor`，拦截 **Executor.query** 方法。它发现 ThreadLocal 里有分页参数，就**改写 SQL**：先执行 `select count(0) from (原SQL) tmp` 拿总数，再给原 SQL 拼上 `limit ?, ?`；
> ③ 返回的 List 被包装成 `Page` 类型，额外携带 `total`、`pageNum` 等字段。
>
> **为什么必须紧跟着执行查询**：分页参数放在 ThreadLocal 里，只对"下一条"查询生效；中间插了别的查询就把参数消耗掉了，导致分页失效或错乱。用完会 `clearPage()` 清理，避免线程复用污染。

**Q2.3** 动态 SQL 里的 `<where>`、`<if>`、`<foreach>`、`<choose>` 各解决什么问题？

> 【答题框架】把自己写的订单搜索 XML 讲一遍，特别是 `<where>` 为什么能自动去掉多余的 and

**我的回答：** 不会

> ✅ **参考答案**：
> - `<if test="条件">`：条件成立才把这段 SQL 拼进去。**注意**：`test` 里是 OGNL 表达式，空字符串要写 `status != null and status != ''`。
> - `<where>`：把内部的条件包起来，**自动删掉开头多余的 `and`/`or`**；如果所有条件都不成立，它连 `where` 关键字都不生成。这就解决了"每个 `<if>` 都写 and，第一个条件命中时会变成 `where and xxx`"的语法错误。（我踩过这个坑：ShoppingCart 的 XML 里 `<if>` 少了 and，直接 SQL 语法错误。）
> - `<foreach>`：遍历集合。属性：`collection`（集合名）、`item`（每次的变量名）、`open`/`close`（包起来的前后缀）、`separator`（分隔符）。用来拼 `in (...)` 或批量 `values (...),(...)`。
> - `<choose>/<when>/<otherwise>`：多选一，相当于 Java 的 `if / else if / else`。订单搜索里用它做"有 orderBy 就按它排序，否则默认按 id 倒序"。
> - 补充：`<set>` 用于 update，自动去掉末尾多余的逗号。

**Q2.4** 批量新增（如订单明细、套餐-菜品关系）怎么写的？为什么不用循环单条插？

> 【答题框架】`<foreach>` 拼 values → 一次网络往返 vs N 次 → 注意点（MySQL 有 SQL 长度限制）

> ✅ **参考答案**：
> 用 `<foreach>` 拼成**一条** insert 多组 values：
> ```xml
> <insert id="insertBatch">
>     insert into order_detail (order_id, name, image, dish_id, setmeal_id, number, amount)
>     values
>     <foreach collection="orderDetailList" item="od" separator=",">
>         (#{od.orderId}, #{od.name}, #{od.image}, #{od.dishId}, #{od.setmealId}, #{od.number}, #{od.amount})
>     </foreach>
> </insert>
> ```
> 为什么不用循环单条插：循环 N 条就是 **N 次数据库网络往返 + N 次 SQL 解析**。批量一条 SQL 只需要 1 次往返，订单有几十个明细时性能差距是几十倍。
> 注意点：① MySQL 有 `max_allowed_packet` 限制，数据量特别大要分批（比如每 1000 条一批）；② 要在同一个事务里，保证要么全成功要么全失败；③ 批量插入不能拿到每条的自增 id（用不上就无所谓）。

**Q2.5** 公共字段（create_time、update_user 等）你是怎么处理的？

> 【考察点】AOP（必考）
> 【答题框架】自定义注解 + AOP 环绕/前置通知 → 反射拿实体 set 值 → 为什么注解要加在 **Mapper 层**（切点表达式是 `com.sky.mapper.*`）

> ✅ **参考答案**：
> 公共字段：`create_time`、`create_user`、`update_time`、`update_user`。
>
> 做法：
> ① 定义注解 `@AutoFill(value = OperationType.INSERT/UPDATE)`；
> ② 写切面 `AutoFillAspect`，切点 `execution(* com.sky.mapper.*.*(..)) && @annotation(autoFill)`；
> ③ 通知里判断是 INSERT 还是 UPDATE：INSERT 填 4 个字段，UPDATE 只填 `update_time`/`update_user`；值通过**反射**调用实体的 setter 设置，`update_user` 从 `BaseContext.getCurrentId()` 拿。
>
> **为什么注解必须加在 Mapper 方法上**：切点表达式限定的是 `com.sky.mapper` 包，注解加在 Service 方法上根本不匹配切点，AOP 不会拦截，字段就一直是 null——我实际踩过这个坑。
>
> 另一种主流做法：MyBatis-Plus 的 `MetaObjectHandler`（在 insertFill/updateFill 里统一赋值），更省事。

**Q2.6** 讲讲全局异常处理器。业务异常和系统异常你怎么区分的？

> 【答题框架】`@RestControllerAdvice` + `@ExceptionHandler` → 自定义 BusinessException 携带友好 msg → 兜底的 Exception 要打日志 + 返回通用提示，不能把堆栈抛给前端

> ✅ **参考答案**：
> 实现：`@RestControllerAdvice` 类 + 若干 `@ExceptionHandler(异常类型)` 方法。
>
> 本项目分两类：
> - **业务异常**（`BaseException` 及其子类，如 `BusinessException`、`OrderBusinessException`、`ShoppingCartBusinessException`）：这类是"用户操作不合法"，比如"菜品正在起售中不能删除""账号不存在"。处理方式：取 `e.getMessage()` 直接返回给前端，`code=0`。**关键设计**：`BaseException` 自己持有 `code` 和 `msg` 字段，所以异常能携带友好提示。
> - **系统异常**（兜底的 `Exception`）：这是程序 bug 或环境问题，用户看不懂也没必要看。处理方式：`log.error("系统异常", e)` 打完整堆栈到日志，**前端只返回"系统繁忙，请稍后再试"**。
>
> 为什么要区分：① 不把堆栈、表名、文件路径暴露给前端（安全隐患）；② 业务异常是"预期内的"，不需要报警，系统异常是"预期外的"，需要日志和告警；③ 前端体验统一。

**Q2.7** 返回值为什么统一用 `Result`？如果不用会怎样？

> ✅ **参考答案**：
> 好处：
> ① **前端处理统一**——一个响应拦截器判断 `code` 就行，不用每个接口写一套解析；
> ② **业务错误和 HTTP 错误分离**——HTTP 依然是 200，业务失败靠 `code=0` + `msg` 表达，前端拿到的是可展示的提示语；
> ③ **易扩展**——想加 traceId、错误类型、国际化只需改这一个类；
> ④ 团队协作有契约，接口文档（Knife4j）自动生成的结构统一。
>
> 不用会怎样：每个接口返回结构各不相同，前端要写 N 套解析；出错时可能直接返回 Spring 默认的错误页（HTML）或堆栈，前端解析不了，用户看到的是白屏或乱码。

**Q2.8** 你项目里怎么做参数校验的？`@Validated` 用了吗？不用行不行？

> ✅ **参考答案**：
> 本项目主要靠 **Service 层手动 if 校验** + 抛业务异常，比如：购物车不能为空、地址簿必须存在、菜品起售中不能删、订单状态必须合法。
>
> `@Validated`（JSR-303 注解，如 `@NotNull`、`@NotBlank`、`@Pattern`）本项目基本没用。不用也能跑，但问题明显：① 校验逻辑散落在各个 Service 方法里，重复代码多、容易漏；② 每个方法都要写一堆 if，代码臃肿。
>
> 更规范的做法：在 DTO 字段上加校验注解 + Controller 参数加 `@Validated`，然后在全局异常处理器里捕获 `MethodArgumentNotValidException` 统一返回错误提示。这样校验和业务逻辑分离，代码干净。

**Q2.9** 新增菜品时，菜品和口味（dish_flavor）是一张表吗？为什么拆开？插入时怎么保证一致？

> 【答题框架】一对多 → 同一事务 → `useGeneratedKeys` 回填主键（你踩过这个点）

> ✅ **参考答案**：
> **不是一张表**。`dish` 是主表，`dish_flavor` 是从表（含 dish_id 外键），一对多关系。
>
> 为什么拆：一个菜品的口味数量不确定（可能是 0 个，也可能是"辣度/甜度/温度"多组），塞进 dish 表没法设计（要么用 JSON 字段、要么预留一堆冗余列，都很难查询和维护）。拆开后结构清晰、可索引可查询。
>
> 插入时怎么保证一致：
> ① `dish` 表的 insert 加 `useGeneratedKeys="true" keyProperty="id"`，MyBatis 会把数据库生成的**自增主键回填**到传入的 `dish` 对象上（这就是为什么插入后能拿到 id）；
> ② 遍历 flavor 列表，给每个 flavor `setDishId(dish.getId())`，批量插入 `dish_flavor`；
> ③ 两个插入放在**同一个 `@Transactional` 方法**里，任何一步失败都回滚，不会出现"菜品插了但口味没插"。

**Q2.10** 修改菜品时，口味怎么处理？为什么不是 update 而是先删后插？

> ✅ **参考答案**：
> 做法：`delete from dish_flavor where dish_id = #{dishId}` 删掉旧口味，再把前端传来的新口味列表批量插入。
>
> 为什么不用 update：前端传来的是**一份完整的新口味列表**，和库里旧的没有稳定对应关系——可能新增了口味、可能删掉了、可能改了名字。要做 update 就得逐条 diff（哪些要删、哪些要改、哪些要加），逻辑复杂、容易漏，而且还要给口味加个稳定的业务主键用来比对。
>
> 先删后插的结果一定是"库里 = 前端传的"，简单且正确。两者放在**同一个事务**里，保证"不会删了没插"导致口味丢失。
> 代价是主键 id 会一直增长、破坏了原有的 id，如果口味 id 被其他表引用就不能这么干（本项目没有）。

### 第 3 轮 · 核心机制（12 题，重点）

**Q3.1** JWT 是什么？为什么用它而不用 Session？两者对比？

> 【考察点】鉴权方案选型（必考）
> 【答题框架】JWT 三段式结构（header.payload.signature）→ 无状态、易水平扩展 → 缺点（无法主动失效、体积大、payload 明文）→ Session 的优缺点和服务端存储问题

> ✅ **参考答案**：
> **JWT = JSON Web Token**，三段用 `.` 连接：`header.payload.signature`。
> - header：算法（HS256）
> - payload：负载，存 userId、用户名、过期时间（**只是 Base64 编码，不是加密，谁都能解开看**）
> - signature：用密钥对前两段签名，**防篡改**——改了 payload 签名就对不上。
>
> 为什么用它而不用 Session：
> - **Session 是有状态的**：数据存在服务端（内存或 Redis），客户端只存一个 sessionId。多台服务器集群时，A 机器创建的 session 在 B 机器上不存在 → 要么做会话粘性（nginx ip_hash），要么把 session 共享到 Redis（等于还是集中存储）。**水平扩展麻烦**。
> - **JWT 是无状态的**：服务端不存任何东西，只验签。多实例天然支持，适合前后端分离和微服务。
> - JWT 还天然适合跨域、跨端（小程序、App、Web 都能用同一个 token）。
>
> JWT 的缺点（面试官想听）：① **签发后无法主动失效**（除非加 Redis 黑名单），用户登出/改密码后旧 token 依然有效；② token 体积比 sessionId 大，每次请求都要带；③ payload 明文，不能放敏感信息；④ 续期机制要自己设计。
>
> 本项目：登录成功后签发 JWT 返回前端，前端存起来，之后每个请求放在请求头里，拦截器解析校验并把 id 放进 `BaseContext`。

**Q3.2** 你项目里为什么是两个拦截器（Admin / User）？

> 【答题框架】两端 token 名称不同（token / authentication）、密钥不同（itcast / itheima）、拦截路径不同（/admin/** 与 /user/**）→ 你曾经把路径写成 `/user/user/**` 导致 BaseContext 拿不到 id，这个坑讲出来很加分

> ✅ **参考答案**：
> 因为**管理员和用户是两套完全独立的身份体系**（`employee` 表 vs `user` 表）：
> | | Admin 拦截器 | User 拦截器 |
> |---|---|---|
> | 拦截路径 | `/admin/**` | `/user/**` |
> | 请求头名 | `token` | `authentication` |
> | 签名密钥 | `itcast` | `itheima` |
> | 校验对象 | employee 表（员工） | user 表（小程序用户） |
>
> 为什么不能合成一个：① 两端前端传 token 的**请求头字段名不同**；② 密钥不同，员工 token 和用户 token 不能互认——如果共用一个拦截器，就有可能出现"用户 token 能访问管理端接口"的**越权**问题；③ 拦截路径不同，登录接口、图片上传这类公开接口要排除在外。
> 解析成功后都往同一个 `BaseContext`（ThreadLocal）里放当前 id，但业务含义不同（一个是员工 id，一个是用户 id）。
>
> **我踩过的坑**：注册 User 拦截器时路径写成了 `/user/user/**`，结果 `/user/shoppingCart/**` 这些接口根本没被拦截 → 拦截器不执行 → `BaseContext.getCurrentId()` 返回 null → 查询条件 `userId = null` → 购物车查不出来。改成 `/user/**` 才正常。

**Q3.3** `BaseContext`（ThreadLocal）是什么？为什么用它？

> 【考察点】ThreadLocal（必考）
> 【答题框架】同一线程内跨层传参，避免每层都传 userId → ThreadLocal 的 key 是线程 → **线程池复用线程会导致数据串用，必须用后 remove**（这是面试官最想听的）

> ✅ **参考答案**：
> `BaseContext` 内部就是一个 `ThreadLocal<Long>`：
> ```java
> public class BaseContext {
>     private static ThreadLocal<Long> threadLocal = new ThreadLocal<>();
>     public static void setCurrentId(Long id) { threadLocal.set(id); }
>     public static Long getCurrentId() { return threadLocal.get(); }
>     public static void removeCurrentId() { threadLocal.remove(); }
> }
> ```
> 用法：拦截器解析 JWT 拿到 id → `setCurrentId(id)`；Service/Mapper 层需要时 `getCurrentId()`。
>
> 为什么用它：一个请求的 userId 从 Controller → Service → ServiceImpl 很多层都要用（查购物车要、下单要、查历史订单要），如果作为方法参数一层层传，方法签名会变得很脏。ThreadLocal 让**同一线程内随处可取**，无侵入。
>
> **最重要的坑（面试官最想听的）**：ThreadLocal 的数据是**绑定在当前线程**上的，而 Tomcat 用线程池复用线程。如果请求结束时不清除，下一个请求复用了同一个线程，就会读到上一个用户的数据——用户 A 可能查到用户 B 的购物车，这是**严重的越权和数据串用**。
> 所以拦截器的 `afterCompletion` 里必须 `BaseContext.removeCurrentId()`。用 `remove()` 而不是 `set(null)`，因为后者在 ThreadLocalMap 里还留着 entry，会内存泄漏。

**Q3.4** 拦截器、过滤器、AOP 三者的区别和使用场景？

> 【答题框架】Filter 在 Servlet 层、Interceptor 在 Spring MVC 层、AOP 在方法层 → 各自能拿到什么、典型用途

> ✅ **参考答案**：
> | 维度 | Filter | Interceptor | AOP |
> |---|---|---|---|
> | 归属 | Servlet 容器 | Spring MVC | Spring 容器 |
> | 拦截范围 | 所有请求（含静态资源、img） | 只拦 Controller 请求 | 任意 Spring Bean 的方法 |
> | 能拿到 | request/response | request/response/**handler（目标方法）/ModelAndView** | **方法签名、参数、返回值** |
> | 执行时机 | DispatcherServlet 之前 | Controller 方法前后 | 方法调用前后 |
> | 典型用途 | 编码、跨域、XSS 过滤、请求日志 | 登录鉴权、权限校验 | 事务、日志、缓存、公共字段填充 |
>
> 本项目：**Filter 基本没用**；**Interceptor 做 JWT 鉴权**（Admin/User 两个，能拿到 request 解析 token，还能在 afterCompletion 里清理 ThreadLocal）；**AOP 做公共字段自动填充**（需要拿到目标方法的参数实体对象，Filter 和 Interceptor 拿不到实体，只能 AOP）。
>
> 一句话选择依据：**要拿方法参数/返回值就 AOP，要拦 HTTP 请求做鉴权就 Interceptor，要在最外层处理（含静态资源）就 Filter**。

**Q3.5** Redis 在你项目里用在哪？为什么要用缓存？

> 【答题框架】菜品/套餐缓存、店铺营业状态、可能还有 token → 读多写少 → 减轻 DB 压力、降低响应时间

> ✅ **参考答案**：
> 项目里的用途：
> ① **菜品列表缓存**——`@Cacheable(cacheNames="dish_", key="#categoryId")`，key 形如 `dish_12`（分类下的菜品列表）；
> ② **套餐列表缓存**——`@Cacheable(cacheNames="setmealCache", key="#categoryId")`；
> ③ **店铺营业状态**——`SHOP_STATUS` 这个 key 存 0/1，商家改营业状态改的就是它。
>
> 为什么用缓存：商品数据是典型的**读多写少**——成千上万的用户频繁浏览菜单，而商家一天可能才改几次。每次浏览都查 MySQL 要经过网络、连接池、磁盘 IO、SQL 解析；命中 Redis 直接内存返回，响应时间和数据库压力差好几个数量级。此外还能保护数据库不被突发流量打垮。
>
> 补充：Redis 是单线程 + 纯内存 + IO 多路复用，所以单机 QPS 轻松上万，非常适合做缓存。

**Q3.6** 缓存是怎么更新/清理的？为什么不用改一个删一个，而是删一堆？

> 【考察点】缓存一致性（必考）
> 【答题框架】`@Cacheable` 的 key 设计（dish_${categoryId}）→ 改菜品会影响哪些 key → 为什么用 `cleanCache("dish_*")` 全清（简单可靠，牺牲一点命中率）→ 追问：更优方案？（按 categoryId 精准删、延迟双删、Canal 订阅 binlog）

> ✅ **参考答案**：
> 查询时用 `@Cacheable` 缓存，key 设计成**按分类**：`dish_<categoryId>`。
> 商家**新增/修改/删除/起售停售菜品**时，调 `cleanCache("dish_*")`：
> ```java
> Set keys = redisTemplate.keys(pattern);   // 用通配符拿到所有匹配的 key
> if (keys != null && keys.size() > 0) redisTemplate.delete(keys);
> ```
>
> 为什么不精准删一个：
> 一个菜品可能出现在**多个缓存 key** 里——它属于某个分类（`dish_12`），如果分类改了就涉及两个分类的 key；套餐的 `setmealCache` 里也包含了菜品信息；菜品还可能有独立详情缓存。要维护"改这个菜要删哪几个 key"的映射关系非常复杂，**一旦漏删就会出现"改了不生效"的脏数据**，这种 bug 极难排查。
> 全清虽然牺牲了缓存命中率、多查几次数据库，但**保证了正确性**——对这个小体量系统，性能损失完全可以接受。这是典型的"正确性优先于性能"的取舍。
>
> 更优方案（面试加分）：① 按 categoryId 精准删（需要对菜品-分类的变更关系做完整梳理）；② 缓存 key 加版本号，改的时候版本号+1；③ **延迟双删**（删缓存 → 更新 DB → 延迟再删一次）；④ 用 **Canal 订阅 MySQL binlog**，异步刷新缓存，业务代码零侵入。

**Q3.7** `@Cacheable`、`@CachePut`、`@CacheEvict` 的区别？

> ✅ **参考答案**：
> - **`@Cacheable`**：**先查缓存**——命中就直接返回缓存值，**不执行方法**；未命中才执行方法，并把返回值写入缓存。用于**查询**。
> - **`@CachePut`**：**每次都执行方法**，然后把返回值写回缓存。用于**新增/修改**。注意 key 必须和查询时一致，否则写了也读不到。
> - **`@CacheEvict`**：**删除**缓存。`@CacheEvict(allEntries = true)` 清空整个 namespace（本项目 `cleanCache` 就是手动实现这个效果）。
>
> 共同点：都靠 Spring 的**代理**生效，所以**同类内部方法自调用（this.xxx()）不走代理，注解会失效**——这是最经典的坑。

**Q3.8** 缓存穿透、缓存击穿、缓存雪崩分别是什么？你项目里怎么防？

> 【答题框架】穿透=查不存在的 key（布隆过滤器/空值缓存）；击穿=热点 key 过期（互斥锁/逻辑过期）；雪崩=大量 key 同时过期（过期时间加随机值）

> ✅ **参考答案**：
> 三个问题的共同点：都是**请求绕过缓存直接打到数据库**，区别在于"为什么没命中"。
>
> - **缓存穿透**：查一个**数据库里根本不存在**的数据（比如 id=-1），缓存永远不命中，每次都打到 DB。恶意攻击常用这招把 DB 打垮。
>   防：① 缓存空值（查到 null 也缓存，设短过期时间）；② **布隆过滤器**（提前把存在的 key 放进去，不存在直接拦掉）；③ 参数合法性校验（id 必须 > 0）。
> - **缓存击穿**：某个**热点 key 恰好过期**的那一瞬间，大量并发同时穿到 DB。
>   防：① **互斥锁**——只让一个线程去回源查 DB 重建缓存，其他线程等待；② **逻辑过期**——缓存不设物理过期，value 里存逻辑过期时间，发现过期了异步重建，其他线程先返回旧数据；③ 热点数据干脆不设过期时间。
> - **缓存雪崩**：**大量 key 在同一时刻集体过期**（比如都是凌晨统一加载、过期时间都设 1 小时），或者 Redis 直接宕机，所有请求瞬间压到 DB。
>   防：① 过期时间加**随机值**打散；② 多级缓存（本地 Caffeine + Redis）；③ Redis 高可用（哨兵/集群）；④ 限流、降级、熔断兜底。
>
> 本项目现状：商品缓存基本不设过期时间或设很长，风险不大；但如果换成秒杀类场景就必须处理这三个问题。

**Q3.9** 你项目里的事务用在哪？`@Transactional` 什么时候会失效？

> 【考察点】事务（必考，也是你项目真实存在的风险点）
> 【答题框架】下单（订单 + 明细一起写）、再来一单 → 失效场景：同类内部方法调用、方法非 public、异常被 catch 吃掉、异常类型不匹配、多数据源/多线程

> ✅ **参考答案**：
> 用在哪：**用户下单**（订单主表 + 明细表 + 清购物车，三步必须同生共死）、**再来一单**、**菜品新增/修改**（菜品 + 口味）、**套餐新增/修改**（套餐 + 套餐菜品关系）、**起售停售**、**报表相关的批量操作**。
>
> `@Transactional` 失效的六大场景：
> ① **同类内部方法自调用**（`this.method()`）——Spring 事务靠 **AOP 代理**实现，自调用不走代理，注解形同虚设。**这是最常见的一个**。解决：注入自己、用 `AopContext.currentProxy()`、或把方法拆到另一个 Service。
> ② 方法**不是 public**——CGLIB 代理无法增强 private/protected 方法。
> ③ **异常被 catch 吞掉**——没抛出去，事务管理器收不到信号，不会回滚。
> ④ **异常类型不匹配**——默认只对 `RuntimeException` 和 `Error` 回滚。抛受检异常（如 `IOException`）不会回滚，要写 `@Transactional(rollbackFor = Exception.class)`。
> ⑤ **多线程/异步**——事务信息存在 ThreadLocal 里，子线程拿不到，新线程里的事务是独立的。
> ⑥ 数据库引擎不支持事务（MyISAM）。
>
> 💡 加分点：主动说"我项目里 `submitOrder` 有 `@Transactional`，但因为同类调用的坑，我后来特意确认过它是从 Controller 直接调进来的，走的代理"。

**Q3.10** 下单流程如果中途失败了会怎样？你怎么保证订单和明细一致？

> ✅ **参考答案**：
> `submitOrder` 方法加了 `@Transactional`，订单主表插入、明细批量插入、清空购物车**在同一个事务里**，任何一步抛异常整体回滚，不会出现"订单创建了但明细没了"这种脏数据。
>
> 但要做得更严谨，还需要补几点：
> ① **`rollbackFor = Exception.class`**——保证受检异常也回滚（默认只回滚 RuntimeException）；
> ② **订单号唯一索引**——防并发重复下单，数据库层面兜底；
> ③ **异常要能抛出去**——不能在下单逻辑里把异常 catch 掉，否则事务收不到信号（这是我项目里要检查的点）；
> ④ 如果后续接了真实支付，还要用**本地消息表/事务消息**保证"订单状态"和"第三方支付结果"最终一致，因为外部调用无法纳入本地事务。

**Q3.11** Spring Boot 自动配置原理？为什么加个 starter 就能用？

> 【答题框架】`@SpringBootApplication` 拆解 → `spring.factories` / `AutoConfiguration.imports` → 条件注解 `@ConditionalOnClass` 等

> ✅ **参考答案**：
> `@SpringBootApplication` 是三个注解的组合：
> - `@SpringBootConfiguration`（本质是 @Configuration，声明这是配置类）
> - `@ComponentScan`（扫描当前包及子包的 Bean）
> - **`@EnableAutoConfiguration`** ← 自动配置的核心
>
> 自动配置链路：
> ① `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 引入选择器；
> ② 选择器读取 classpath 下所有 jar 的 **`META-INF/spring.factories`**（Spring Boot 2.7）或 **`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`**（Spring Boot 3.x）文件，拿到几百个自动配置类的全限定名；
> ③ 这些配置类**不是全部生效**，靠**条件注解**按需装配：`@ConditionalOnClass`（classpath 有这个类才生效）、`@ConditionalOnMissingBean`（用户没自己定义才生效）、`@ConditionalOnProperty`（配置项满足才生效）等。
>
> 所以"加个 starter 就能用"的真相是：**starter 本身只是"引依赖的空壳"**（比如 `mybatis-spring-boot-starter` 只是把 mybatis、jdbc、自动配置都引进来了），真正的配置逻辑在配套的 autoconfigure 模块里预置好了。比如引入 mybatis starter 后，`MybatisAutoConfiguration` 检测到 classpath 有 SqlSessionFactory 类，就自动帮你创建好 `SqlSessionFactory`、扫描 Mapper。

**Q3.12** Bean 的生命周期和循环依赖？

> 【答题框架】实例化 → 属性填充 → 初始化 → 使用 → 销毁；三级缓存如何解决循环依赖；你项目里 `allow-circular-references: true` 就是踩过这个坑

> ✅ **参考答案**：
> **生命周期（简化版）**：
> ① 实例化（调构造方法，此时对象还没属性）
> ② 属性填充（依赖注入，`@Autowired` 在这一步）
> ③ Aware 接口回调（BeanNameAware/BeanFactoryAware 等）
> ④ `BeanPostProcessor.postProcessBeforeInitialization`
> ⑤ 初始化（`@PostConstruct` → `InitializingBean.afterPropertiesSet` → 自定义 init-method）
> ⑥ `BeanPostProcessor.postProcessAfterInitialization` ← **AOP 代理对象在这里生成**（这就是为什么 AOP 基于代理，自调用会失效）
> ⑦ 使用
> ⑧ 销毁（`@PreDestroy` → `DisposableBean.destroy`）
>
> **循环依赖**：A 依赖 B，B 又依赖 A。Spring 用**三级缓存**解决：
> - 一级 `singletonObjects`：成品 Bean
> - 二级 `earlySingletonObjects`：半成品（已实例化未完成属性填充）
> - 三级 `singletonFactories`：ObjectFactory（**能提前暴露 AOP 代理**）
>
> 流程：创建 A → 实例化后把 A 的工厂放进三级缓存 → 填充属性发现要 B → 创建 B → B 填充属性要 A → 从三级缓存拿到 A 的早期引用（需要代理就提前生成代理放二级缓存）→ B 创建完成 → A 继续填充完成。
>
> **注意**：只解决"单例 + 字段/setter 注入"；**构造器注入的循环依赖解决不了**（对象还没实例化就没法提前暴露）；原型（prototype）Bean 也解决不了。
>
> 我项目 `application.yml` 里开了 `spring.main.allow-circular-references: true`，说明确实存在循环依赖（比如某些 Service 互相注入）。**这本质上是设计问题**——更规范的做法是抽出第三方 Service 或引入事件机制打破环。

**Q4.1** 讲一下用户下单的完整流程，从点击"去支付"到订单落库。

> 【考察点】业务理解 + 异常处理（这道题能讲 5 分钟）
> 【答题框架】校验地址簿 → 校验购物车非空 → 校验起售状态 → 校验配送范围 → 构造订单（金额怎么算？配送费、打包费）→ 插入订单拿主键 → 明细批量插入 → 清空购物车 → 返回 OrderSubmitVO

> ✅ **参考答案**：
> `OrderServiceImpl.submitOrder()`，**全程在一个 `@Transactional` 里**：
> ① 取当前用户 id（`BaseContext.getCurrentId()`）
> ② 查地址簿 `addressBookMapper.getById(addressBookId)`，为 null → 抛 `AddressBookBusinessException("地址簿信息为空")`
> ③ 查购物车 `shoppingCartMapper.list(shoppingCart)`，为空 → 抛 `ShoppingCartBusinessException("购物车数据为空")`
> ④ 校验店铺营业状态、菜品/套餐是否起售（本项目部分做了）
> ⑤ 调用 `checkOutOfRange(address)` 用百度地图算店铺到收货地址的驾车距离，超过 5000 米 → 抛"超出配送范围"
> ⑥ **构造 Orders 对象**：订单号（时间戳）、`status=1`（待付款）、`payStatus=0`（未支付）、user_id、address_book_id、`orderTime=now`、amount（**服务端重算**）、phone/address/consignee（从地址簿**复制快照**）、打包费、餐具数、预计送达时间
> ⑦ `orderMapper.insert(orders)`——XML 里配了 `useGeneratedKeys="true" keyProperty="id"`，**主键回填**到 orders 对象
> ⑧ 遍历购物车，把每一项转成 `OrderDetail`（`setOrderId(orders.getId())`），收集成 List，最后 `orderDetailMapper.insertBatch(list)` **批量插入**
> ⑨ `shoppingCartMapper.deleteByUserId(userId)` **清空购物车**
> ⑩ 返回 `OrderSubmitVO`（订单 id、订单号、订单金额、下单时间）
>
> 💡 表述技巧：按"校验 → 组装 → 落库 → 清理 → 返回"五段说，逻辑清楚；主动提"整个过程在一个事务里"。

**Q4.2** 订单金额是怎么算出来的？为什么要服务端重算而不是信前端传的金额？

> 【考察点】安全意识（很加分）
> 【答题框架】前端传来的金额可被篡改 → 服务端必须根据购物车/菜品表重算

> ✅ **参考答案**：
> 金额构成：`amount = Σ(每项购物车记录的 amount × number) + 打包费 + 配送费`。
>
> **绝对不能信前端传的金额**：HTTP 请求是可以被篡改的（抓包改参数、改 JS 改前端逻辑），如果后端直接用前端传来的金额落库，用户把 100 元改成 1 元商家就亏了。这是最典型的**越权/参数篡改漏洞**。
>
> 原则：**所有涉及钱和权限的计算，都必须在服务端基于可信数据（数据库）重新计算**。前端传的金额最多用来做一次"不一致就报错"的校验，或者纯粹用于展示。
>
> 同理，下单时商品单价也应该以 `dish`/`setmeal` 表的**当前价格**为准，而不是购物车里存的旧价格（商家可能在下单前调过价）。

**Q4.3** 订单有哪几个状态？状态之间怎么流转？

> 【考察点】状态机（必考）
> 【答题框架】1 待付款 → 2 待接单 → 3 已接单 → 4 派送中 → 5 已完成 / 6 已取消 → 每一格谁能操作、要校验什么 → 推销：用状态机模式/枚举替代散落的 if

> ✅ **参考答案**：
> 状态常量（`Orders` 类）：`1 待付款`、`2 待接单`、`3 已接单`、`4 派送中`、`5 已完成`、`6 已取消`。
>
> 流转图：
> ```
> 1 待付款 --支付成功--> 2 待接单 --商家接单--> 3 已接单 --派送--> 4 派送中 --完成--> 5 已完成
> 1 待付款 --用户取消/超时--> 6 已取消
> 2 待接单 --用户取消/商家拒单--> 6 已取消（已付款需退款）
> 3/4 --商家取消--> 6 已取消（需退款）
> ```
>
> 每个操作的合法前置状态（本项目实际实现）：
> | 操作 | 要求的前置状态 | 说明 |
> |---|---|---|
> | 支付成功 → 待接单 | 必须 == 1 | 支付回调里改 |
> | 用户取消 | <= 2 | 状态 2 时需退款 |
> | 商家拒单 | 必须 == 2 | 需退款 |
> | 商家接单 | == 2 | |
> | 派送 | 必须 == 3 | |
> | 完成 | 必须 == 4 | 写 delivery_time |
> | 商家取消 | 任意进行中 | 需退款 |
>
> 为什么必须校验前置状态：不校验的话，对一条"已完成"的订单点"接单"，状态会被改回 3，直接乱套；财务上也会算错营业额。
>
> **加分改进**：现在每个操作里都是一堆 `if (status != X) throw`，散落各处容易漏。更好的做法是用**枚举 + 状态转移表**（`Map<当前状态, Set<允许的下一个状态>>`）统一校验，或引入状态机框架（Spring StateMachine），把"谁能流转到谁"配置化。

**Q4.4** 商家接单/拒单/派送/完成，各自要改哪些字段？为什么要先查再改？

> 【答题框架】先 getById 拿现状 → 校验状态合法 → update 只改必要字段（动态 SQL 的好处）

> ✅ **参考答案**：
> | 操作 | status | 其他字段 |
> |---|---|---|
> | 接单 | 2 → 3 | — |
> | 拒单 | 2 → 6 | `rejection_reason`、`cancel_time`、`pay_status=2`(退款) |
> | 派送 | 3 → 4 | — |
> | 完成 | 4 → 5 | `delivery_time` |
> | 商家取消 | * → 6 | `cancel_reason`、`cancel_time`、退款 |
>
> **为什么先查再改**（三个原因）：
> ① **校验前置状态**——只有查出来才知道当前是几，才能判断"这一步合不合法"；
> ② **拿业务数据**——要订单号（退款用）、支付状态（决定要不要退款）；
> ③ **判断存在性**——`getById` 返回 null 说明订单不存在，直接抛异常。
>
> 改的时候只 `new Orders()` 设 `id` + 本次要改的字段，靠 **XML 里的动态 SQL `<if test="xxx != null">`** 只更新非空字段——这样不用先查完整对象再全字段 update，也不会把没传的字段覆盖成 null。

**Q4.5** 拒单/取消订单时用户已经付过钱怎么办？

> 【答题框架】调微信退款 → 支付状态置 REFUND → 你项目里是模拟的，要能说清楚"真实场景怎么做 + 我为什么用模拟"

> ✅ **参考答案**：
> **真实场景**：
> ① 判断 `pay_status == 1`（已支付）才需要退款；
> ② 调用微信退款 API：`weChatPayUtil.refund(商户订单号, 商户退款单号, 退款金额, 原订单金额)`；
> ③ 退款成功（或受理成功）后，把 `pay_status` 改成 `2`（REFUND），订单状态改成 `6`，记录取消/拒单原因和取消时间；
> ④ 用户端看到"已退款"。
>
> **这里有个重要的工程问题**（加分点）：退款是**外部调用**，可能超时、可能失败。不能简单地把它和本地事务绑在一起——本地事务回滚了，钱可能已经退出去，无法撤销。规范做法是：先落一条"退款申请记录"，调微信退款，定时任务做补偿和对账，保证最终一致。
>
> **我项目里的做法**：没有真实的微信商户号/证书，`weChatPayUtil.refund` 一定会抛异常。所以我把它改成打一行日志 + 直接把 `pay_status` 置为 2，**模拟退款成功**的效果。
> 面试时主动说明："我知道真实场景该怎么调，也知道外部调用要做幂等和补偿；我砍掉这一段是因为没有商户资质，不是不会。"

**Q4.6** 超时未支付的订单怎么处理？

> 【答题框架】Spring Task 定时扫（status=1 且 order_time < now-15min）→ 追问：为什么不用延迟队列？（RabbitMQ 死信队列 / Redis ZSet / 时间轮）→ 集群下定时任务重复执行怎么办？（分布式锁 / xxl-job）

> ✅ **参考答案**：
> **本项目做法**：`OrderTask` 定时任务（`@Scheduled(cron = "0 * * * * ?")` 每分钟执行一次），调用 `getByOrderStatusAndOrderTimeLT(1, now - 15min)`，把查出来的待付款超时订单批量改成 `6 已取消`（真实电商还要回补库存/优惠券）。
> 对应的 SQL：`select * from orders where status = 1 and order_time < #{time}`。
>
> **更优方案：延迟队列**——下单时往 RabbitMQ 发一条**延迟 15 分钟**的消息（死信队列 TTL 或延迟插件），到期消费检查订单是否仍为待付款，是则取消。
> 优点：**精确到秒**、不用空扫数据库、削峰。定时任务扫表的缺点是：精度取决于执行频率（每分钟扫一次就有最多 1 分钟误差）、每次都全表/索引扫描、量大时对数据库有压力。
>
> **集群下的坑（必问）**：多实例部署时，`@Scheduled` 在**每台机器上都会执行一遍**，同一个订单可能被处理多次。解决：
> ① 用 **Redis 分布式锁**保证同一时刻只有一个实例执行；
> ② 用 **xxl-job / ElasticJob** 这类分布式调度平台，天然支持分片和单点执行；
> ③ 让任务本身**幂等**（`update orders set status=6 where status=1 and id=?`，重复执行结果一样）。

**Q4.7** WebSocket 来单提醒是怎么做的？

> 【答题框架】@ServerEndpoint + 每客户端一个 session 存 map → 商家端连上后推消息 → 为什么不用轮询（资源浪费、实时性差）→ 追问：多实例部署怎么办？（Redis 发布订阅 / MQ 广播）

> ✅ **参考答案**：
> **实现**：
> ① `WebSocketServer` 用 `@ServerEndpoint("/ws/{sid}")` 声明端点；`@OnOpen` 时把 `sid` 和 `Session` 存进一个 `ConcurrentHashMap<String, Session>`（每个客户端一个会话）；`@OnMessage`/`@OnClose` 做对应处理。
> ② 商家端连接后，`sid` 绑定到该店员。
> ③ 有**新订单**（用户支付成功）或**催单**时，Service 调 `webSocketServer.sendToAllClient(JSON字符串)`，遍历 map 里所有 session 发消息（`session.getBasicRemote().sendText(msg)`）。
> ④ 前端收到消息后弹窗 + 播放语音播报。消息体里用 `type` 区分：`type=1` 来单提醒，`type=2` 客户催单。
>
> **为什么不用轮询**：轮询要么间隔长（实时性差，商家要等几秒才知道来单）要么间隔短（每个商家每秒发一次请求，连接和带宽浪费巨大）。WebSocket 是**全双工长连接**，服务端可以主动推送，实时且省资源。
>
> **追问：多实例部署怎么办？** 现在 session 存在**单机内存**里——商家连在 A 机器上，订单在 B 机器产生，A 上的 map 里没有这个 session，消息就丢了。解决：用 **Redis 发布订阅**或 **MQ 广播**把消息发到所有实例，各实例再推给自己持有的连接；或者网关层做会话粘性。

**Q4.8** 购物车的设计：为什么 shopping_cart 表要有 dish_id、setmeal_id、dish_flavor 三个字段？

> 【答题框架】菜品和套餐共存 → 同一菜品不同口味算两条 → 用唯一组合判断"已存在则数量+1"

> ✅ **参考答案**：
> `shopping_cart` 表字段：`user_id`、`dish_id`、`setmeal_id`、`dish_flavor`、`number`、`amount`、`name`、`image`。
>
> 三个字段的作用：
> - **`dish_id` 和 `setmeal_id` 二选一**：购物车既能放**菜品**也能放**套餐**，所以需要两个字段分别标识（而不是一个字段 + 一个类型字段）。加购菜品时填 dish_id、setmeal_id 为 null，反之亦然。
> - **`dish_flavor`**：同一道菜**不同口味要算两条记录**（"宫保鸡丁-微辣"和"宫保鸡丁-中辣"是两个不同的购物车条目，价格可能也不同），所以口味必须参与"是否已存在"的判断。
>
> **为什么冗余存 name / image / amount**：前端购物车列表要直接展示商品名、图片、单价，如果每次都去关联查 dish/setmeal 表，N 条购物车就是 N 次关联查询，又慢又复杂。冗余一份就是**快照**，展示直接拿来用。
>
> **加购逻辑**：以 `user_id + dish_id/setmeal_id + dish_flavor` 为条件查，**存在则 number+1，不存在则新增一条**——这就是为什么这三个字段必须是判断的组成部分。

**Q4.9** "再来一单"怎么实现的？和直接下单有什么区别？

> ✅ **参考答案**：
> **实现**（`OrderServiceImpl.repetition(Long id)`）：
> ① 取当前用户 id
> ② `orderDetailMapper.getByOrderId(id)` 查出原订单的所有明细
> ③ 用 stream + `BeanUtils.copyProperties(x, shoppingCart, "id")` 把每个 `OrderDetail` 转成 `ShoppingCart`（**第三个参数 "id" 表示忽略 id 字段**，其他同名字段自动复制：name、image、amount、number、dishId、setmealId、dishFlavor）
> ④ 补上 `userId` 和 `createTime`
> ⑤ `shoppingCartMapper.insertBatch(list)` 批量插入购物车
>
> **和直接下单的区别**：再来一单**不下单**，它只是把商品**重新加回购物车**，用户还要自己去购物车确认、选地址、再点提交订单。本质上是"重新加购"和"提交订单"两个动作被分开了。
>
> **缺陷（加分点）**：本项目没处理"原菜品已下架或已删除"的情况——如果菜没了，加购会失败或加进一个无效商品。更严谨的做法是逐个校验商品当前状态，跳过不合法的。

**Q4.10** 用户催单做了什么？

> 【答题框架】查订单 → WebSocket 推给商家端 → 语音播报 → 你踩过的坑：定时任务每 5 秒重复播报，应该是事件驱动而不是轮询

> ✅ **参考答案**：
> **流程**：C 端调 `/user/order/reminder/{id}` → Service 查订单是否存在 → 通过 WebSocket 给商家端推一条消息（`type=2`）→ 商家端弹窗 + 语音播报"客户催单了"。
>
> **我踩过的坑（这是很好的面试素材）**：
> 我最初把来单提醒写成了 `@Scheduled(cron = "0/5 * * * * ?")`——每 5 秒扫一次待接单订单然后播报。结果**每 5 秒就重复播报一次，停不下来**，商家被语音轰炸。
> 根因：① 把**事件驱动**写成了**轮询**——来单/催单是"某一刻发生的事件"，应该在事件发生的那一刻主动推一次；② 就算要轮询，也没有状态位标记"这条已经提醒过了"，导致同一条反复播。
> 正确做法：在**订单支付成功**和**用户点催单**这两个事件点上主动调 WebSocket 推送。（如果要保留扫表兜底，也必须加"已提醒"标记。）
>
> 💡 面试价值：这个 bug 说明我理解"事件驱动 vs 轮询"的区别，而且能讲清楚排查过程。

**Q4.11** 报表统计里，营业额/订单数/用户数是怎么算的？

> 【答题框架】按天循环 → 构造 map 传 begin/end/status → `sumByMap` / `countByMap` → 时间区间用 `LocalTime.MIN` 和 `MAX` 的坑

> ✅ **参考答案**：
> **共同套路**：先把 `[begin, end]` 每一天展开成一个 `List<LocalDate>`，然后**按天循环**，每天构造一个 Map 传条件，调 Mapper 查当天的数据，最后把结果列表用 `StringUtils.join(list, ",")` 拼成逗号分隔的字符串塞进 VO（前端 ECharts 要的就是这种格式）。
>
> - **营业额**（`TurnoverReportVO`）：每天 `map{begin=当天00:00, end=次日00:00, status=5}` → `orderMapper.sumByMap(map)` → `select sum(amount) from orders where order_time >= ? and < ? and status = 5`。查出来 null 要转成 0。
> - **用户统计**（`UserReportVO`）：每天查两次 `userMapper.countByMap`——**总用户数**（`create_time < 次日0点`）和**新增用户数**（`create_time >= 当天0点 and < 次日0点`）。
> - **订单统计**（`OrderReportVO`）：每天查**订单总数**（不限状态）和**有效订单数**（status=5），再对列表求和得到区间总数，完成率 = 有效订单数 / 订单总数（除数为 0 要防）。
>
> **我踩过的坑**：
> ① **时间类型不匹配**——`LocalDate` 和 `LocalDateTime` 混用导致编译报错，`LocalTime.MIN` 是 `00:00:00`，`MAX` 是 `23:59:59.999999999`；
> ② **区间边界问题**——营业额那里用的是 `>= begin and <= end`（闭区间），相邻两天会在边界上重复统计；规范做法统一用**左闭右开** `>= begin and < end`；
> ③ 列表为空时 `stream().reduce(Integer::sum).get()` 会抛异常，要先判空。

**Q4.12** Excel 导出怎么做的？如果模板文件不存在会怎样？

> 【答题框架】POI XSSF 读模板 → 填单元格 → 写 outputstream → 踩过的坑：`getResourceAsStream` 返回 null 导致 NPE、参数要 HttpServletResponse

> ✅ **参考答案**：
> **流程**：
> ① 确定时间范围（最近 30 天），调 `workspaceService.getBusinessData(begin, end)` 拿概览数据 VO；
> ② `getClass().getClassLoader().getResourceAsStream("template/运营数据报表模板.xlsx")` 从 **classpath** 读模板（文件放在 `src/main/resources/template/`）；
> ③ `new XSSFWorkbook(in)` 基于模板创建 Excel 对象 → `excel.getSheet("Sheet1")` 拿工作表；
> ④ 用**行列坐标**填数据：`sheet.getRow(1).getCell(1).setCellValue(...)`（**行号列号从 0 开始**）；
> ⑤ `response.getOutputStream()` 拿响应输出流 → `excel.write(out)` → `close()`。浏览器就收到一个下载文件。
>
> **模板不存在会怎样**：`getResourceAsStream` 找不到文件时**返回 null 而不是抛异常**，紧接着 `new XSSFWorkbook(null)` 直接抛 **NPE** → 接口 500。这是最容易踩的坑：编译期完全没问题，运行才发现。所以模板必须保证在 `resources/template/` 下。
>
> **我踩过的坑**：方法参数类型写成了 `HttpServletRequest`，但 `getOutputStream()` 是 **响应对象**的方法（请求对象只有 `getInputStream()`），**编译都过不了**。必须是 `HttpServletResponse`，而且要**三处一起改**（接口、实现类、Controller）。

### 第 5 轮 · 进阶与架构（10 题）

**Q5.1** 项目现在这套架构有什么问题？如果日订单量到 100 万，哪里会先崩？

> 【考察点】架构敏感度（高级岗必问）
> 【答题框架】单库单表 → 订单表分库分表；同步下单链路 → 引入 MQ 异步；本地缓存 → Redis；定时任务 → 分布式调度；单点 → 集群 + 网关

> ✅ **参考答案**：
> 按"先崩的顺序"说，比较有画面感：
> ① **数据库最先崩**：orders 单表一天 100 万，一年 3.6 亿行，索引再大也扛不住 → **分库分表**（按 user_id 或 order_time 分片，用 ShardingSphere）、冷热数据分离、历史订单归档。
> ② **下单链路太同步**：一次下单要校验、插订单、插明细、发通知、算报表，响应时间长 → 把**非核心步骤异步化**（发通知、积分、统计走 MQ），核心链路只保留"创建订单"。
> ③ **定时任务**：单机 `@Scheduled` 扫全表会越来越慢 → **分布式调度 + 分片**（xxl-job），或改延迟队列。
> ④ **WebSocket 单机 map**：多实例下消息只推给一台机器上的商家 → **Redis 发布订阅 / MQ 广播**。
> ⑤ **报表实时聚合**：`sum/count` 扫大量数据打 DB → **预计算**（定时跑批写统计表）或换 **ClickHouse/ES** 做分析。
> ⑥ **应用单点**：一台 8080 挂了服务就没了 → 多实例 + 网关 + 负载均衡 + 限流熔断（Sentinel）。
> ⑦ 业务层还有：**库存超卖**（乐观锁/Redis 预扣）、**重复下单**（幂等）、**分布式事务**。
>
> 💡 回答框架："先数据库 → 再应用 → 再中间件 → 最后架构"，面试官会觉得你有体系。

**Q5.2** 下单接口怎么防重复提交（幂等）？

> 【答题框架】前端按钮防抖只是辅助 → 服务端：唯一订单号 + 唯一索引、Redis 分布式锁、token 机制

> ✅ **参考答案**：
> 前端做的（按钮置灰、防抖）**只是体验优化，不算方案**——用户可以绕过前端直接发请求。
>
> 服务端的几种做法：
> ① **唯一索引兜底**：orders 表的 `number`（订单号）加**唯一索引**，重复插入直接抛 `DuplicateKeyException`。这是最后一道防线，最可靠。
> ② **Redis 分布式锁**：key 用 `用户id + 业务标识`，`SETNX` 加锁成功才处理。适合"同一用户短时间内只能提交一次"。
> ③ **Token 机制**（推荐）：进入订单确认页时后端生成一个 token 存 Redis 并返回，提交订单时带上 token，服务端用**原子操作**（`DEL` 返回 1 才算成功）验证并删除——第二次提交时 token 已经不在了，直接拒绝。这天然实现了"一次性凭证"。
> ④ **状态校验**：已是"已支付"的订单再次支付请求直接拒绝。
>
> 下单场景建议 **Token 机制（防并发重复） + 唯一索引（兜底）** 双保险。

**Q5.3** 分布式锁怎么实现？Redis 做分布式锁有什么坑？

> 【答题框架】SETNX + 过期时间 → 原子性、误删别人锁（value 存唯一标识 + Lua）、锁续期（看门狗）、Redisson

> ✅ **参考答案**：
> **基本实现**：`SET key value NX PX 30000`
> - `NX`：key 不存在才能设置成功（互斥）
> - `PX 30000`：30 秒自动过期（防死锁）
> - `value`：存一个唯一标识（如 UUID），标识"锁是谁持有的"
>
> **释放锁**：不能直接 `DEL`，必须先用 Lua 脚本**判断 value 是自己的**再删——否则可能删掉别人刚拿到的锁。
> ```lua
> if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
> ```
>
> **四个坑（面试重点）**：
> ① **加锁和设过期必须原子**（用一条 `SET NX PX`，早期分两步会死锁）；
> ② **锁过期了业务还没执行完** → 别人拿到锁 → 需要**自动续期**（Redisson 的看门狗机制，默认每 10 秒续一次）；
> ③ **释放锁要校验持有者**（Lua 保证原子）；
> ④ **Redis 主从切换会丢锁**（主节点挂了还没同步给从节点）→ Redis 官方 RedLock 方案（但争议较大）或多副本 + 多数派。
>
> **生产实践**：直接用 **Redisson** 的 `RLock`，上面这些它都封装好了。其他方案：ZooKeeper 临时顺序节点、数据库唯一索引。

**Q5.4** 如果要用消息队列，你会用在哪些地方？

> 【答题框架】下单异步（扣库存、发通知）、超时订单延迟队列、订单状态变更通知、报表异步导出

> ✅ **参考答案**：
> ① **下单异步化**：下单成功后，发通知（短信/公众号模板消息）、WebSocket 推送给商家、加积分——这些和"创建订单"没有强一致要求，丢到 MQ 里异步做，主链路响应更快。
> ② **超时订单延迟队列**：替代每分钟扫表的定时任务，精确、不空扫（RabbitMQ 死信队列 / 延迟插件、RocketMQ 定时消息）。
> ③ **订单状态变更事件**：订单完成 → 通知统计服务、积分服务、数据仓库订阅消费，实现业务解耦。
> ④ **报表异步导出**：导出数据量大时不阻塞请求，后台生成文件，完成后通知用户下载。
> ⑤ **削峰填谷**：用餐高峰期下单请求暴增，MQ 做缓冲，后端按自己的消费能力处理。
>
> **选型**：RabbitMQ（延迟队列成熟、中小规模首选）、RocketMQ（事务消息、顺序消息、阿里系）、Kafka（高吞吐，适合日志/埋点）。
> **注意**：引入 MQ 就要承担"消息丢失、重复消费、顺序性"这些新问题（消费端必须**幂等**）。

**Q5.5** 接口怎么限流？怎么防止刷单？

> ✅ **参考答案**：
> **限流的算法**：
> - 计数器：简单，但有临界问题（1 秒的边界上可能放过 2 倍流量）
> - 滑动窗口：解决临界问题
> - 漏桶：恒定速率流出，削峰但不允许突发
> - **令牌桶**：按速率生成令牌，允许一定突发 —— **最常用**（Guava RateLimiter、Sentinel）
>
> **限流的层次**：
> - 网关层：Nginx `limit_req`、Spring Cloud Gateway + Sentinel
> - 应用层：Sentinel / Resilience4j 的注解、AOP + Redis 计数器
> - **分布式限流**：Redis + Lua 实现令牌桶（多实例共享计数）
> - 维度：按 IP、按用户 id、按接口、全局
>
> **防刷单**：① 下单频次限制（同一用户 X 秒内只能下一单）；② 设备指纹 / 风控；③ 手机号验证、图形验证码；④ 优惠券用唯一索引防止重复领取；⑤ 黑名单 + 规则引擎；⑥ 关键接口签名防重放。

**Q5.6** 慢 SQL 怎么排查？你会给哪些字段加索引？

> 【答题框架】explain → 索引失效场景 → 你项目里 orders 表的 user_id、status、order_time 该不该加索引

> ✅ **参考答案**：
> **排查步骤**：
> ① **定位**：开启慢查询日志（`slow_query_log`，`long_query_time` 设 1 秒）、Druid 监控面板、APM（SkyWalking）、`show processlist` 看当前卡住的 SQL；
> ② **分析**：`EXPLAIN` 看关键列——
>    - `type`：要 `range`/`ref`/`eq_ref`，出现 **`ALL` 就是全表扫描**
>    - `key`：实际用了哪个索引（null 说明没用上）
>    - `rows`：预估扫描行数，越小越好
>    - `Extra`：出现 `Using filesort`（额外排序）、`Using temporary`（用临时表）要优化
> ③ **优化**：加索引、改写 SQL、减少回表、分页优化。
>
> **索引失效的常见场景**：对索引列做函数运算或类型隐式转换（`where DATE(create_time)=?`）、`like '%xx'` 前置通配、复合索引不满足**最左前缀**、`or` 连接非索引列、`!=`/`not in`/`is null`（视情况）。
>
> **本项目该加索引的字段**：
> - `orders`：`user_id`（历史订单按用户查）、`status`（状态统计）、`order_time`（报表按时间范围）、`number`（唯一索引，防重）
> - `order_detail`：`order_id`
> - `shopping_cart`：`user_id`
> - `dish`：`category_id`
>
> **深分页问题**：`limit 100000, 10` 会先扫 10 万行再丢弃。优化：① **延迟关联**（先用覆盖索引查出 10 个主键，再 join 回表）；② **游标法**（`where id > 上一页最后一个 id limit 10`）。

**Q5.7** 前后端分离下怎么解决跨域？你项目里有跨域问题吗？

> ✅ **参考答案**：
> **什么是跨域**：浏览器的**同源策略**——协议、域名、端口三者任一不同就是跨域，浏览器会拦截响应。
>
> **本项目其实没有跨域问题**：前端跑在 nginx（80 端口），接口请求走**同源的 nginx**（`/api/` 被 nginx 反向代理到 `localhost:8080/admin/`），浏览器看到的就是同源请求。**这也正是用 nginx 反代而不是让前端直连 8080 的原因之一**。
>
> 如果确实跨域，解决方案：
> ① **后端 CORS**：`WebMvcConfigurer.addCorsMappings()` 或 `@CrossOrigin` 注解，配置 allowOrigins / allowMethods / allowHeaders；
> ② **前端代理**：开发环境用 `vue.config.js` 的 devServer.proxy 转发；
> ③ **nginx 反代**（本项目用的就是这个，最干净）。
>
> **注意**：CORS 的预检请求（OPTIONS）要放行，不能拦截；且 `allowCredentials=true` 时 `allowOrigins` 不能写成 `*`。

**Q5.8** 项目怎么部署？nginx 起了什么作用？

> 【答题框架】nginx 反向代理 + 静态资源托管 + /api 前缀重写 → 为什么要分离前端静态资源和后端接口

> ✅ **参考答案**：
> **B 端**：前端打包成静态文件，放在 nginx 的 `html/sky` 目录，由 `location /` 直接返回；**C 端**是微信小程序，由微信平台托管，不走 nginx。
>
> **nginx 的五个作用**：
> ① **静态资源服务器**：托管前端 dist，性能远好于后端 Tomcat 返回静态文件；
> ② **反向代理**：`location /api/` → `http://localhost:8080/admin/`（顺便**重写了 /api 前缀**），`location /user/` → 后端 C 端接口；
> ③ **WebSocket 代理**：`location /ws/` 配了 `Upgrade`/`Connection` 头做协议升级，否则 WebSocket 握手会失败；
> ④ **负载均衡**：`upstream webservers` 可配多个后端实例；
> ⑤ 可加 gzip 压缩、缓存、限流、HTTPS 卸载。
>
> **为什么分离**：前端可独立部署和更新（改前端不用重启后端）、后端可多实例扩展、nginx 作为统一入口屏蔽内网结构、能统一做安全策略。
>
> 生产环境会更进一步：Docker 打镜像 → docker-compose / K8s 编排 → 前面再加一层 SLB/云负载均衡。

**Q5.9** 线上出了问题怎么排查？日志、链路追踪你怎么做的？

> ✅ **参考答案**：
> **日志**：用 logback 分级输出（info 记业务、error 记异常）并按天滚动；关键链路打**带业务标识的日志**（订单号、用户 id），异常打完整堆栈。生产环境用 **ELK**（Filebeat 采集 → ES 存储 → Kibana 检索）或 Loki 集中收集。
>
> **指标监控**：**Prometheus + Grafana** 看 QPS、响应时间（P99）、错误率、JVM（堆内存、GC、线程数）、数据库连接池、Redis 命中率；配置告警（Alertmanager）。
>
> **链路追踪**：**SkyWalking / Zipkin** 自动埋点，一次请求生成 `traceId`，串起经过的所有服务和每一段耗时，快速定位瓶颈在哪个环节。
>
> **排查套路**：用户报障 → 拿到时间点和订单号 → 按 traceId 捞出完整日志链路 → 看监控指标是否有突增（QPS/RT/错误率） → 查数据库慢 SQL/锁等待 → 看是否刚发版（回滚验证）。
>
> **本项目现状**：只有 Lombok `@Slf4j` 输出到控制台，**没有任何监控和链路追踪**，这是最大的工程化短板——面试可以主动承认并说出改进方向。

**Q5.10** 怎么保证接口安全？现在这套 JWT + 拦截器还缺什么？

> 【答题框架】HTTPS、越权校验（C 端只能查自己的订单）、敏感信息脱敏、接口签名、限流

> ✅ **参考答案**：
> **现在已经有的**：JWT 鉴权（拦截器校验 token）、密码 MD5 加密存储、SQL 用 `#{}` 预编译防注入、`BaseContext` 传递当前用户。
>
> **缺什么（缺口就是考点）**：
> ① **水平越权校验（最严重）**——C 端"查订单详情"这类接口，必须校验"这条订单属不属于当前用户"。否则用户改一下 URL 里的 id 就能看别人的订单和地址。本项目部分接口靠 `userId` 作为查询条件间接实现了隔离，但**按 id 直接查的接口是裸的**。
> ② **没有 HTTPS**：token 明文传输，能被中间人截获。
> ③ **没有 RBAC 权限模型**：现在只有"登录了没"，没有"这个员工能不能删菜品"。员工表有 role 字段但没真正用起来。
> ④ **没有接口签名/防重放**：时间戳 + nonce + 签名，防请求被截获后重放。
> ⑤ **没有限流、验证码、登录失败锁定**：密码可以暴力破解。
> ⑥ **敏感信息**：返回给前端的对象不能包含 password；日志里不能打密码和 token。
> ⑦ JWT 无法主动失效（需要 Redis 黑名单支持"强制下线"）。

### 第 6 轮 · 前沿视角（2026 年面试的加分项，8 题）

**Q6.1** Spring Boot 2.7 到 Spring Boot 3.x 有哪些破坏性变化？升级要注意什么？

> 【答题框架】Java 17 基线、`javax.*` → `jakarta.*`、自动配置注册文件变化、Spring Security 6 写法变化、可观测性（Micrometer）

> ✅ **参考答案**：
> ① **Java 基线从 8/11 提到 17**（最低 17）。语言层面可以用 record、密封类、文本块、switch 表达式。
> ② **`javax.*` → `jakarta.*`**（**迁移成本最大的点**）：Servlet、Validation、Persistence、Annotation 全部改包名。本项目里的 `javax.servlet.http.HttpServletRequest`、`ServletOutputStream` 都要改成 `jakarta.servlet.*`。
> ③ **自动配置注册文件变了**：从 `META-INF/spring.factories` 改为 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。
> ④ **Spring Security 6**：`WebSecurityConfigurerAdapter` 被移除，全面改为基于 `SecurityFilterChain` Bean 的组件式配置。
> ⑤ **配置属性有重命名和移除**，要过一遍官方迁移指南。
> ⑥ 配套生态要一起升级：MyBatis 用的是 `mybatis-spring-boot-starter` 3.x；**Knife4j/springfox 已不维护，要换成 springdoc-openapi**（这是升级时最容易卡住的地方）。
> ⑦ 新增可观测性支持（Micrometer Observation）。

**Q6.2** 如果重做这个项目，认证鉴权你会怎么做？

> 【答题框架】Spring Security / Sa-Token、OAuth2、JWT + Redis 黑名单、令牌刷新、RBAC 权限模型（现在你只有"是否登录"，没有"有没有权限"）

> ✅ **参考答案**：
> ① **框架**：换 **Spring Security 6**（标准、生态好）或 **Sa-Token**（国内轻量、注解式鉴权、学习成本低，适合中小项目）。
> ② **权限模型改 RBAC**：`user` / `role` / `permission` 三张表 + 关联表，接口级鉴权 `@PreAuthorize("hasAuthority('dish:delete')")`。现在只有"登录与否"，连"员工能不能删菜品"都控制不了。
> ③ **JWT 增强**：**短效 accessToken（15 分钟） + 长效 refreshToken（7 天）**；Redis 存**黑名单**支持主动登出和强制下线；token 里不放敏感信息。
> ④ **微服务下**：网关统一鉴权，服务内部只信任网关透传的用户信息（`X-User-Id` 请求头），不再各自解析 token。
> ⑤ **安全加固**：登录失败次数锁定、图形验证码、密码用 BCrypt（而不是 MD5）、异地登录提醒。

**Q6.3** 微服务化怎么拆？

> 【答题框架】用户服务、商品服务、订单服务、支付服务、统计服务 → Nacos 注册配置中心、OpenFeign 调用、Gateway 网关、Sentinel 限流熔断、Seata 分布式事务

> ✅ **参考答案**：
> **服务划分**（按业务域）：用户服务、商品服务（分类/菜品/套餐）、购物车服务、订单服务、支付服务、配送服务、统计服务、通知服务。
>
> **基础设施**：
> - **Nacos**：注册中心 + 配置中心（服务发现、动态配置）
> - **Spring Cloud Gateway**：统一入口，做路由、鉴权、限流
> - **OpenFeign**：服务间声明式调用（配 Sentinel 做熔断降级）
> - **Sentinel**：限流、熔断、降级
> - **Seata**：分布式事务（AT/TCC 模式）
> - **SkyWalking**：链路追踪
>
> **真实难点**：
> ① **分布式事务**——下单要"扣库存 + 建订单"跨两个服务，不能简单用本地事务。方案：Seata 或**最终一致**（本地消息表 + MQ）
> ② **跨服务查询**——订单列表要展示菜品名，不能跨服务 join，用**冗余快照**（order_detail 里已经存了 name，正好）
> ③ **数据一致性**——服务间的数据同步（用户信息变更怎么同步到订单服务）
>
> **重要提醒（加分点）**：**别为了微服务而微服务**。单体在业务量不大时运维成本低、开发效率高、排查简单。只有团队规模大了、不同模块需要独立扩容或独立迭代时，拆微服务的收益才大于成本。

**Q6.4** 除了 MySQL + Redis，还有什么存储你会考虑？

> 【答题框架】ES 做商品搜索（现在 like 模糊查询会全表扫）、MongoDB 存订单快照、ClickHouse 做报表分析

> ✅ **参考答案**：
> - **Elasticsearch**：**商品搜索**。现在 `dish.name like '%宫保%'` 是**全表扫描 + 不支持分词**，用户搜"宫爆鸡丁"（错别字）、"鸡丁"、"gongbao"都搜不到，也没有相关度排序。ES 的**倒排索引 + 中文分词器 + 拼音插件**能实现模糊、纠错、高亮、按相关度排序。这是最该引入的。

> - **对象存储（OSS）**：图片文件（项目已经在用）。
> - **HBase**：海量订单明细的存储。
>
> **选型原则**：按**访问模式**和**数据结构**选，不是越多越好——每引入一个存储就多一份运维成本和数据一致性负担。

**Q6.7** 微信支付的完整流程是什么？（你现在是模拟的）

> 【答题框架】统一下单 → 获取 prepay_id → 小程序拉起收银台 → 微信异步回调 notify → 验签 → 改订单状态 → 回调必须幂等

> ✅ **参考答案**（小程序 JSAPI 支付）：
> ① 小程序调 `wx.login` 拿 code → 后端用 code 换 **openid**（本项目已实现）。
> ② 用户点"支付" → 后端调微信**统一下单** API（传商户号、订单号、金额、openid、回调地址 notify_url），拿到 **`prepay_id`**。
> ③ 后端把 prepay_id 等参数**再次签名**后返回给小程序（不能把密钥给前端）。
> ④ 小程序调 `wx.requestPayment` 拉起微信收银台，用户完成支付。
> ⑤ 微信服务器向 notify_url **异步回调**——**注意：订单状态的修改必须以这个回调为准，绝不能信前端说"我支付成功了"**。
> ⑥ 后端在回调里：**验签** → 校验金额和订单号是否匹配 → 修改订单状态为"待接单"、`pay_status=1` → 给微信返回成功应答（否则微信会重复通知）。
>
> **三个关键点（面试官必问）**：
> - **订单状态以回调为准**（前端不可信）
> - **回调必须幂等**（微信会重复通知）：先查订单状态，已处理就直接返回成功
> - **回调要防伪造**：验签 + 校验金额
> - 生产还要处理"支付成功但回调丢失"的补偿（定时主动查单）
>
> **本项目为什么模拟**：没有商户号和证书，拿不到 prepay_id，所以我把 ④⑤ 两步砍掉，在 `payment()` 里直接调 `paySuccess(orderNumber)`，模拟"微信回调已到达"的效果。前端也相应跳过了 `wx.requestPayment`，改成直接弹"支付成功"再跳转。
> **面试话术**：主动说清"真实链路是怎样的、我砍掉了哪一段、为什么砍"，比支支吾吾强得多。

## 第七部分：做功能的通用套路（复盘手册）

> 这一部分是**操作手册**——下次接到任何新需求，照着顺序走就行。
> 核心心法：**从外往里**（先确定前端要什么，再倒推代码），不要一上来就打开 IDE 写。

### 7.1 七步法总览

| 步骤 | 做什么 | 产出 | 关键判断 |
|---|---|---|---|
| ① **找接口** | 前端调的是哪个 URL | 路径 + 方法 + 参数 + 返回 | 去前端 JS 里 grep，**别猜** |
| ② **定数据** | 涉及哪些表 | 表名 + 字段 + 关系 | 要写几张表？→ 决定要不要事务 |
| ③ **定模型** | 入参 / 出参 | DTO / VO | 和 Entity 差在哪 |
| ④ **写 Mapper** | 数据怎么读写 | 接口方法 + SQL | 注解还是 XML？ |
| ⑤ **写 Service** | 业务逻辑、校验 | 接口 + 实现 | 要事务吗？要缓存吗？ |
| ⑥ **写 Controller** | 暴露 HTTP 接口 | 各层注解 | **路径必须和前端对上** |
| ⑦ **自测联调** | 验证 | 编译通过 + 返回正确 | **重启了吗？** |

**为什么是这个顺序**：
- ①②③是"想清楚"，④⑤⑥是"写下来"。**大部分返工都发生在跳过①②③直接写代码**——写完才发现前端要的返回结构和你想的不一样，或者漏了一张表。
- 自测放最后不是不重要，而是它检验前面六步。**联调失败时，倒着往回查**（先看 Controller 路径对不对 → 再看 SQL 参数对不对 → 再看业务逻辑）。

### 7.2 七步详解

#### ① 找接口 —— 永远不要猜前端要什么

本项目前端静态包在：`D:\develop\sky-nginx\nginx-1.20.2\html\sky\js\`

在里边 grep 中文提示语或方法名（比如搜 `催单`、`conditionSearch`），能找到前端真实请求的路径。

**要记录四件事**：
1. **URL**：`/api/report/ordersStatistics`
2. **HTTP 方法**：GET / POST / PUT / DELETE
3. **参数位置**：query（`?page=1`）、body（JSON）、path（`/details/{id}`）
4. **返回结构**：前端拿哪个字段用（`res.data.records` 还是 `res.data`）

⚠️ **nginx 会重写前缀**：前端写 `/api/report/xxx`，nginx 转成后端 `/admin/report/xxx`（去掉 `/api`，加上 `/admin`）。**写 Controller 的 `@RequestMapping` 时要用重写后的路径**，这是 404 的高发区。

#### ② 定数据 —— 先看表，再想代码

```
desc orders;      -- 看字段
show create table orders;   -- 看索引和注释
```

判断三件事：
- **读哪些表**：要不要关联？（菜品列表要关联分类表拿 `categoryName`）
- **写哪些表**：**写 ≥ 2 张表就要考虑 `@Transactional`**
- **有没有现成的 Entity**：有就复用，没有才新建

#### ③ 定模型 —— 什么时候该建 DTO / VO

| 情况 | 做法 |
|---|---|
| 入参和 Entity 完全一致 | **直接用 Entity**，不要多建一个类 |
| 入参比 Entity 多（分页参数）或少（只要 id） | 建 **DTO** |
| 入参字段名和 Entity 对不上 | 建 **DTO** |
| 返回需要**拼接/组装**（`orderDishes`、`categoryName`） | 建 **VO** |
| 返回需要**脱敏**（`password` 不能给前端） | 建 **VO** |
| 返回就是一张表的全部字段且不敏感 | 可以用 Entity（本项目多处分页直接返回 Entity） |

> 判断口诀：**能用 Entity 就用，需要变形才建 DTO/VO**。不要为了"规范"给每个接口都造一对 DTO/VO——那是过度设计。

#### ④ 写 Mapper —— 注解还是 XML？

| 情况 | 选择 | 例子 |
|---|---|---|
| 单表 + 无动态条件 + SQL 短 | **注解** `@Insert`/`@Select` | `countStatus`、`getByOrderId` |
| 多表关联 / 动态条件 / SQL 长 | **XML** | `pageQuery`、`sumByMap` |

**返回值类型怎么定**：
| 查询结果 | 返回类型 |
|---|---|
| 单条 | `Xxx`（查不到返回 null） |
| 多条 | `List<Xxx>`（查不到返回空集合，**不是 null**） |
| 分页 | `Page<Xxx>`（配合 PageHelper） |
| 聚合（count/sum） | `Integer` / `BigDecimal`（**可能返回 null，要判空**） |

**参数怎么传**：多个参数用 `Map` 或 `@Param`；动态 SQL 的条件一般用 Map 传（本项目 `sumByMap(Map map)`、`countByMap(Map map)`）。

⚠️ **别忘**：XML 文件要放在 `src/main/resources/mapper/`，且 `mybatis.mapper-locations` 要配对这个路径。

#### ⑤ 写 Service —— 先校验，再业务

标准写法：

```java
@Service
@Slf4j
public class XxxServiceImpl implements XxxService {

    @Autowired private XxxMapper xxxMapper;

    @Transactional                    // ← 只有写多表才需要
    public XxxVO doSomething(XxxDTO dto) {
        // 1. 取当前用户（如果需要）
        Long userId = BaseContext.getCurrentId();

        // 2. 校验 —— 不合法就抛业务异常，绝不 return null 了事
        Xxx xxx = xxxMapper.getById(dto.getId());
        if (xxx == null) {
            throw new XxxBusinessException("XXX不存在");
        }
        if (!xxx.getStatus().equals(期望状态)) {
            throw new XxxBusinessException(MessageConstant.ORDER_STATUS_ERROR);
        }

        // 3. 组装要写的对象（只 set 要改的字段）
        Xxx update = Xxx.builder().id(dto.getId()).status(新状态).build();

        // 4. 落库
        xxxMapper.update(update);

        // 5. 返回
        return ...;
    }
}
```

**校验抛什么异常**：先用项目里现成的（`BusinessException`、`OrderBusinessException`、`ShoppingCartBusinessException`），不够再新建，但**新的一定要继承 `BaseException`**（否则全局异常处理器抓不到友好提示）。

| 前端怎么传 | 后端怎么接 |
|---|---|

#### ⑦ 自测联调 —— 这步的坑最多

```
① 编译        → 无报错
② 重启服务    → 【最容易忘】不重启 = 跑的是旧 class，改了等于没改
③ Knife4j 测  → http://localhost:8080/doc.html，能看接口也能直接调
④ curl 直连   → 绕过 nginx，区分"前端问题"还是"后端问题"
⑤ 前端联调    → F12 看 Network，对比请求路径
```

**排查用的对照表（背下来）**：

| 现象 | 说明 |
|---|---|
| curl 直连返回 **401** | ✅ 映射存在，只是没带 token —— 后端没问题 |
| curl 直连返回 **404** | ❌ 后端根本没有这个映射 —— 检查 `@RequestMapping` 路径 |
| curl 通了、前端 404 | ❌ 前端调的路径和你的不一样 —— 去 JS 里 grep |
| 返回 200 但数据为空 | ❌ 大概率是 **SQL 条件太严 / 库里没数据**，不是代码问题 |

> 💡 本次实践中这两个坑都踩过：`orderStatistics` vs `ordersStatistics` 差个 s（前端 404、后端 401）；改完代码没重启，一直跑旧 class。

### 7.4 六个"常驻决策点"

每写一个功能，都要过一遍这六个问题：

| # | 要不要做 | 判断依据 | 本项目例子 |
|---|---|---|---|
| 1 | **`@Transactional`** | 一次请求要写 **≥2 张表**或 ≥2 行 | 下单（订单+明细+清购物车）、新增菜品（菜品+口味） |
| 2 | **`@Cacheable`** | **读多写少** | 菜品/套餐列表（用户狂刷，商家偶尔改） |
| 3 | **`@AutoFill`** | 表里有 `create_time`/`create_user`/`update_*` | 几乎所有 insert/update |
| 4 | **拦截器是否排除** | 这个接口**不用登录**吗？ | 登录、图片上传、公开的商品浏览 |
| 5 | **要不要 DTO / VO** | 入参和 Entity 不一致，或返回要拼装/脱敏 | `OrdersPageQueryDTO`、`OrderVO` |
| 6 | **要不要清缓存** | 这次操作会不会让缓存变脏？ | 菜品增删改/启停售 → `cleanCache("dish_*")` |

### 7.6 三个复杂功能的完整拆解

#### A. 用户下单（写操作里最复杂的）

**① 找接口**
```
POST /user/order/submit
body: { addressBookId, payMethod, remark, estimatedDeliveryTime, deliveryStatus, tablewareNumber, tablewareStatus, packAmount, amount }
返回: OrderSubmitVO { id, orderNumber, orderAmount, orderTime }
```

**② 定数据** —— 读 2 张表（`address_book`、`shopping_cart`），写 3 张表（`orders`、`order_detail`、`shopping_cart` 清空）→ **必须 `@Transactional`**

**③ 定模型**
- 入参用现成的 `OrdersSubmitDTO`
- 返回建 `OrderSubmitVO`（不是直接返回 `Orders`，因为订单号、金额这些要单独包装）

**④~⑥ 分层落地**，业务逻辑顺序（这是最有价值的部分）：

```
submitOrder(OrdersSubmitDTO dto)
├─ 1. 取 userId = BaseContext.getCurrentId()
├─ 2. 查地址簿 getById(addressBookId)
│     └─ null → throw AddressBookBusinessException
├─ 3. 查购物车 list(userId)
│     └─ 空 → throw ShoppingCartBusinessException
├─ 4. 校验配送范围 checkOutOfRange(address)      ← 百度地图
├─ 5. 组装 Orders
│     ├─ number = 时间戳（订单号）
│     ├─ status = 1（待付款）、payStatus = 0（未支付）
│     ├─ amount = Σ(单价×数量) + 打包费 + 配送费   ← ★ 服务端重算，不信前端
│     ├─ phone / address / consignee = 从地址簿复制（★ 快照）
│     └─ orderTime = now
├─ 6. orderMapper.insert(orders)                ← ★ useGeneratedKeys 回填 id
├─ 7. 遍历购物车 → List<OrderDetail>
│     ├─ setOrderId(orders.getId())             ← ★ 用回填的 id
│     └─ orderDetailMapper.insertBatch(list)    ← ★ 批量插入
├─ 8. shoppingCartMapper.deleteByUserId(userId) ← ★ 清空购物车
└─ 9. return new OrderSubmitVO(...)
```

**这一步的三个"为什么"（面试必问）**：
- **为什么金额要重算**：前端传的金额可被篡改（抓包改 JS），服务端必须基于可信数据重算
- **为什么地址要快照**：用户以后改了地址，历史订单必须保留下单当时的样子
- **为什么清购物车要放在同一个事务**：否则可能出现"订单创建了但购物车没清"，用户重复下单

#### B. 订单条件搜索（读操作里最复杂的）

**难点**：条件**全是可选的**（可能只按时间查，也可能只按状态查），而且要**给每条订单拼出菜品串**。

**分两步想清楚**：

**第一步：SQL 怎么动态拼** —— 用 `<where>` + `<if>`：
```xml
<select id="pageQuery" resultType="com.sky.vo.OrderVO">
    select o.*, a.consignee, a.phone, a.address from orders o
    left join address_book a on o.address_book_id = a.id
    <where>
        <if test="number != null and number != ''">and o.number like concat('%', #{number}, '%')</if>
        <if test="phone != null and phone != ''">and o.phone like concat('%', #{phone}, '%')</if>
        <if test="status != null">and o.status = #{status}</if>
        <if test="beginTime != null">and o.order_time &gt;= #{beginTime}</if>
        <if test="endTime != null">and o.order_time &lt;= #{endTime}</if>
    </where>
</select>
```

**第二步：`orderDishes` 字段怎么来** —— 这个字段数据库里**没有**，要查完再拼：
```
PageHelper.startPage(...)
Page<OrderVO> page = orderMapper.pageQuery(dto)
├─ 遍历每条 orderVO
│   ├─ 查明细 orderDetailMapper.getByOrderId(orderVO.getId())
│   ├─ stream().map(x -> x.getName() + "*" + x.getNumber() + ";")
│   ├─ String.join("", list)
│   └─ orderVO.setOrderDishes(...)
└─ return new PageResult(page.getTotal(), page.getResult())
```

**这里的关键意识**：**数据库查出来的对象不一定能直接返回**，需要再做一层组装。这就是为什么要有 VO。

#### C. 报表统计（Excel 导出同理）

**统一套路**（营业额 / 用户数 / 订单数 三个接口完全同构）：

```
① 解析时间区间 [begin, end]（LocalDate）
② 把区间展开成每一天：List<LocalDate> dateList
③ 按天循环：
     for (LocalDate date : dateList) {
         构造 Map 条件 { begin: 当天00:00, end: 次日00:00, status: 5 }
         调 mapper 查当天的值
         null 要转成 0                     ← ★ 聚合函数可能返回 null
         加进结果列表
     }
④ 把结果列表拼成逗号分隔字符串：StringUtils.join(list, ",")   ← ★ 前端画图要的格式
⑤ 封装成 VO 返回
```

**导出比统计多两步**：
```
⑥ 读模板 → new XSSFWorkbook(in) → getSheet("Sheet1")
⑦ 按坐标 setCellValue → response.getOutputStream() → excel.write(out)
```

**三个坑**：
- 聚合查询返回 **null**（当天没订单），直接参与运算会 NPE
- 时间区间边界用**左闭右开**更规范（闭区间会让相邻两天重复统计边界数据）
- 导出方法的参数必须是 **`HttpServletResponse`**（请求对象没有 `getOutputStream()`）
