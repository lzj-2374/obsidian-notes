## 三、登录模块

### Q1 为什么用 token 而不用 Session？

> 集群部署下 Session 不共享，要么 Session 复制要么粘性会话，都麻烦；放到 Redis 里集中存储，任何节点都能校验。而且 App/小程序没有 Cookie，token 放请求头更通用。
>
> 流程：登录成功生成 UUID 当 token，用户信息以 Hash 存 Redis（key: `login:token`，TTL 30 分钟）；前端每次请求带 `authorization` 头，拦截器校验通过后把用户存进 ThreadLocal，并**刷新 TTL**。

### Q2 为什么要刷新 token 有效期？

> 只要用户持续访问就续期，活跃用户不会被中途踢下线；长期不访问的 token 自动过期，兼顾安全和体验。

### Q3 拦截器为什么要两个？【高频，能答出来是加分项】

> 第一个拦截器（RefreshTokenInterceptor）负责解析 token、存 ThreadLocal、刷新有效期，**放行所有请求**（包括不需要登录的首页）；第二个（LoginInterceptor）只判断 ThreadLocal 里有没有用户，没有才拦截。
> 如果只用一个拦截器，要么拦截路径太宽导致静态资源也要 token，要么太窄导致只有登录后的路径才刷新有效期。拆成两个是为了**职责分离 + 精确控制拦截范围**。

### Q4 ThreadLocal 有什么问题？

> 内存泄漏。ThreadLocalMap 的 key 是弱引用、value 是强引用，线程池的线程长期存活，value 回收不掉。所以在拦截器的 `afterCompletion` 里 `UserHolder.removeUser()`，请求结束必清理。

## 四、缓存模块（核心，必问）

### Q5 缓存穿透怎么解决的？

> 查询**数据库里根本不存在**的数据，缓存永远不命中，每次都打到数据库。
> 两个方案：①缓存空值——查库不存在就往 Redis 写一个 `""` 加短 TTL；②布隆过滤器。项目里用的①：两次判断，`isNotBlank` 命中真实数据，`!= null` 命中空值标记直接返回。

### Q6 空值为什么用 `""` 不用 `null`？

> Redis 里没有 null，`StringRedisTemplate` 序列化 null 会报错，所以约定 `""` 作为空值标记。TTL 设 2 分钟而不是 30 分钟，是防止数据库后来新增了这条数据，缓存长时间返回旧的不一致结果。

### Q7 缓存击穿怎么解决？两个方案怎么选？【高频】

> **一个热点 key 过期的一瞬间**，大量并发直接打到数据库。
> - **互斥锁**：查不到就 `setIfAbsent` 抢锁，抢到的查库重建缓存，没抢到的休眠重试。强一致，但有等待、锁有 TTL。
> - **逻辑过期**：不设物理 TTL，value 里存 `expireTime`。发现逻辑过期后抢锁，抢到的**异步线程池重建**，所有请求先返回旧数据。高可用不阻塞，但有短暂不一致，且**必须预热**。
>
> 选型：一致性要求高用互斥锁，可用性要求高用逻辑过期。我的项目里商户查询用的逻辑过期，封装在 CacheClient 里通过参数切换。

### Q8 逻辑过期为什么要预热？【你的真实 bug，讲出来很加分】

> 逻辑过期方案里，缓存不存在时**直接返回 null，不查库**。不预热 = 用户查不到数据。我踩过：没预热商铺缓存，页面店名显示 NaN，curl 接口发现 `{"success":true}` 但没有 data，定位是 `cache:shop:1` 不存在，把预热方法加到测试类跑一遍才恢复。

### Q9 缓存雪崩呢？

> 大量 key **同时过期**或 Redis 宕机，请求全打到数据库。解决：TTL 加随机值打散、Redis 集群保高可用、限流降级兜底、多级缓存。

### Q10 缓存和数据库一致性怎么保证？【延伸】

> 先更新数据库、再删除缓存（Cache Aside），配合 TTL 兜底。极端情况下删缓存失败会有短暂不一致，可以用延迟双删或 Canal 监听 binlog 异步删除，我的项目规模用 TTL 兜底够了。

## 五、全局唯一 ID

### Q11 为什么不用数据库自增？

> ①规律性太明显，容易被推算订单量；②单表自增，分库分表后会重复。

### Q12 为什么不用 UUID？

> 无序，作为主键插入 InnoDB 的 B+ 树会导致频繁页分裂，性能差；字符串长，索引占空间。

### Q13 你的 ID 是怎么设计的？【核心】

> `1 bit 符号位（恒 0）+ 31 bit 秒级时间戳 + 32 bit 序列号`。
> 时间戳 = 当前秒 − 自定义起始秒（从 0 开始省位数）；序列号用 Redis `INCR`，key 按天（`icr:order:yyyy:MM:dd`），每天从 1 开始，方便按天统计订单量，也避免单 key 无限膨胀。
> 拼接：`timestamp << 32 | count`。
> 压测：300 线程 × 100 个 = 3 万个 ID **零重复**，QPS 7000+，瓶颈在 Lettuce 连接池 `max-active: 10`，不在算法。

### Q14 为什么用位运算，不用字符串拼接？

> ①返回类型要 long；②字符串拼接没有固定宽度会撞——`时间戳=1,序号=23` 和 `时间戳=12,序号=3` 拼出来都是 `"123"`；③`<< 32` 把时间戳挪到高位（long 定长 64 位，多余自动截断），`|` 把序号填进低 32 位，两段互不重叠。口诀：**左移腾位置，按位或填序号**。

## 六、秒杀模块（最核心，问得最深）

### Q15 库存超卖怎么解决？

> 原因：查库存和扣库存不是原子的。两个线程同时读到 stock=1，都判断通过，都扣减，库存变 −1。
> 解决：乐观锁 CAS——update 时加 `stock > 0` 条件，数据库原子执行 `SET stock=stock-1 WHERE stock>0`，影响行数为 0 就返回失败。

### Q16 乐观锁和版本号法的区别？

> 版本号法加 `version` 字段，`WHERE version=旧值`，每次 +1，还能防 ABA；CAS 不加字段，直接拿业务值（stock）当条件，实现简单，但语义弱——只能判断"还有没有"。我项目里用 CAS，因为扣库存场景只需要"还有库存才扣"。

### Q17 一人一单怎么实现的？为什么会超卖成"一人多单"？

> 下单前按 `user_id + voucher_id` 查订单数，`count > 0` 拦截。**必须两个条件一起查**：只按券查会变成全服一券一单，只按用户查会变成一人一生一单。
> 并发问题：两个请求同时查到 count=0，都放行，都插入。因为这是 **INSERT**，插入前没有行可以加条件，乐观锁用不上，所以用**悲观锁**：按 userId 加锁让同一用户串行，不同用户互不阻塞。

### Q18 锁对象为什么用 `userId.toString().intern()`？

> `synchronized` 比较的是对象地址。`Long` 只有 -128~127 有缓存，超出范围每次装箱都是新对象；`toString()` 每次也 new 新 String。`intern()` 从字符串常量池取相同内容的唯一引用，保证同一用户拿到同一把锁。

### Q19 集群下 synchronized 为什么失效？【高频】

> 锁状态存在 JVM 自己的内存里（对象头 Mark Word + Monitor），多实例各一份互不可见。Nginx 把同一用户的两个请求分发到不同机器，各自都加锁成功，照样重复下单。
> **结论：锁状态需要跨进程共享，就必须用分布式锁。**

### Q20 Redis 分布式锁怎么实现的？

> `SET key value NX EX`（对应 `setIfAbsent`），互斥靠 NX，防死锁靠 EX。
> **value 存线程标识**：`JVM 级 UUID 前缀 + 线程 id`。为什么加 UUID——线程 id 只在单个 JVM 内唯一，集群两台机器都有"线程 37"，只存线程 id 会误删别人的锁。
> key 设计：`lock:` 前缀 + 业务名 + 业务 id，如 `lock:order:101`。

### Q21 释放锁为什么要用 Lua？【必问，准备时间线】

> Java 版是 `get` → `equals` → `delete` 三步，中间可能被打断。时间线：
> ①A 判断 value 是自己的，通过；②A 的锁恰好 TTL 到期自动释放；③B 抢到锁；④A 执行 delete——**删掉的是 B 的锁**；⑤C 又能进来。
> Redis 执行 Lua 是单线程串行的，脚本期间不会插入其他命令，把「比较 + 删除」变成不可分割的整体。**Lua 的原子性不是把多步变一步，而是执行期间不被打断。**

### Q22 你的锁还有什么不足？Redisson 了解吗？【诚实答】

> 三个不足：①不可重入，同线程二次获取会死锁；②业务执行超过 TTL，锁提前释放（看门狗续期能解决）；③获取失败只能循环重试。
> Redisson 用 Hash 结构记录重入次数实现可重入，看门狗每 10 秒续期到 30 秒，还有 pub/sub 等锁唤醒。**项目里我用的是手写 SETNX + Lua（为了理解原理），生产上会选 Redisson。**

### Q23 秒杀链路做了什么优化？【待学，学完跑通再讲】

> 原版：查券 → 判时间 → 判库存 → 扣库存 → 建订单，全部串行查 MySQL，响应慢。
> 优化：Lua 脚本一次性完成「查库存 → 判一人一单 → 预减库存」，资格校验完全不碰 MySQL；通过后发消息队列，异步线程消费落库。主流程只做资格判断 + 入队，响应从百毫秒级降到毫秒级，数据库只承受真实下单量。
> ⚠️ 这部分要能答上追问：消息丢失怎么办（持久化 + 确认机制）、重复消费怎么办（幂等，业务唯一键）、消费失败怎么办（重试 + 死信队列）。**学完再写进简历和话术。**

## 七、大概率被顺带问到的八股

### Q24 Redis 为什么快？

> 纯内存操作；单线程避免锁竞争和上下文切换；IO 多路复用（epoll）让单线程处理大量连接；高效数据结构（SDS、跳表、ziplist、dict 渐进式 rehash）。

### Q25 Redis 持久化？

> RDB：定时快照，bgsave fork 子进程 + 写时复制，恢复快、可能丢最后一次快照后的数据；AOF：追加写命令日志，everysec 最多丢 1 秒，文件大、恢复慢；4.0+ 支持混合持久化。

### Q26 过期删除和内存淘汰？

> 过期删除：惰性删除（访问时检查）+ 定期删除（随机抽样）；内存淘汰：内存满时按策略淘汰，默认 noeviction，常用 allkeys-lru。

### Q27 @Transactional 什么时候失效？

> 六种：自调用绕过代理、方法非 public、异常被 catch 吞掉、异常类型默认只回滚 RuntimeException、类没被 Spring 管理、跨线程。
> **结合项目讲**：我在一人一单里踩过自调用——外层方法直接 `this.createVoucherOrder()`，事务不生效；改成 `AopContext.currentProxy()` 走代理，并且把锁加在无事务的外层方法，让锁包住事务的提交。

## 八、"项目中遇到的最大困难"（必问，用真实 bug）

**推荐讲这个（最完整）：锁误删**

> - **背景**：一人一单用分布式锁，释放锁时先判断是不是自己的锁再删除。
> - **问题**：Java 版 get/equals/delete 三步之间，锁恰好 TTL 到期被别的线程抢走，原线程执行 delete 会误删别人的锁，导致又有线程进来，一人一单失效。
> - **定位**：画时间线推出来的，先怀疑判断逻辑，后来意识到是「判断」和「删除」不是原子操作。
> - **解决**：把比较和删除写进 Lua 脚本，Redis 单线程执行保证原子；value 用「JVM 级 UUID + 线程 id」保证跨实例唯一。
> - **验证**：JMeter 并发下同一用户只有一条订单。

**备选两个**（被问"还有吗"时用）：
1. **逻辑过期没预热**：页面 NaN → curl 发现接口 success 但无 data → 定位到逻辑过期不查库 → 加预热方法
2. **零日期异常**：秒杀券没填 begin_time/end_time，存成 `0000-00-00`，MySQL 驱动转 LocalDateTime 抛异常 → UPDATE 修正数据 + 养成显式传时间的习惯
