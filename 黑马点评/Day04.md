## 一、什么是缓存

缓存就是数据交换的缓冲区（Cache），是存储数据的**临时地方**，一般**读写性能较高**。

**作用**：

1. 降低后端负载
2. 提高读写效率、降低响应时间

**成本**：

1. 数据一致性成本
2. 代码维护成本
3. 运维成本

## 二、添加 Redis 缓存

### 2.1 原理

在客户端和数据库之间加一层 Redis：

- 客户端请求先访问 Redis，**命中**就直接返回
- 没命中就去数据库查，查到后**返回给客户端并把数据写入 Redis**，下次就不用再查库

本质上是用"多一次网络访问"换掉"一次数据库访问"，大大减轻数据库压力。

### 2.2 根据 id 查询商铺的流程

```
开始 → 提交商铺 id → 从 Redis 查缓存 → 是否命中？
    ├─ 命中   → 返回商铺信息 → 结束
    └─ 未命中 → 根据 id 查数据库 → 商铺是否存在？
                    ├─ 不存在 → 返回 404
                    └─ 存在   → 写入 Redis → 返回商铺信息 → 结束
```

### 2.3 String / Hash 两种操作器的固定套路

**铁律：Redis 有 5 种数据结构，操作器一一对应，存取必须匹配。选错操作器要么取到 null，要么直接报错。**

| Redis 结构 | 操作器 |
| --- | --- |
| string | `opsForValue()` |
| hash | `opsForHash()` |
| list | `opsForList()` |
| set | `opsForSet()` |
| zset | `opsForZSet()` |

**怎么判断用哪个**：看当初怎么存的（存取同操作器）。不确定就用 `TYPE key` 看 Redis 里实际是什么结构。

**经验规则（String vs Hash 怎么选）**：

- 要按字段拆开读 / 改（比如登录用户：改昵称、刷 TTL）→ **Hash**（`login:token:xxx`）
- 整个对象打包存取、没有单字段更新需求 → **String + JSON**（`cache:shop:xx`）

#### 套路一：String 类型（对象整体 JSON 存取）

Redis 的 String value 只能存字符串，Java 对象必须经 JSON"翻译"：

```
Java 对象 ──序列化成JSON──> 字符串 ──> 存进 Redis
Java 对象 <──反序列化JSON── 字符串 <── 从 Redis 取
```

口诀：**"出门翻译进去，进来翻译出来"**（存取两段代码互逆，记一段另一段自然推出）

```java
// 存：对象 → JSON 字符串 → Redis（缓存必加 TTL）
String json = JSONUtil.toJsonStr(shop);
stringRedisTemplate.opsForValue().set(key, json, ttl, TimeUnit.MINUTES);

// 取：Redis → JSON 字符串 → 对象
String json = stringRedisTemplate.opsForValue().get(key);
Shop shop = JSONUtil.toBean(json, Shop.class);
```

`opsForValue()` 常用方法：

| 方法 | 作用 |
| --- | --- |
| `set(key, value)` | 存 |
| `set(key, value, timeout, unit)` | 存 + 设过期（缓存必用） |
| `get(key)` | 取 |
| `setIfAbsent(key, value, timeout, unit)` | 不存在才存（分布式锁用） |
| `delete(key)` | 删 |
| `expire(key, timeout, unit)` | 续期 |

**为什么用 JSON 不用 JDK 序列化**：JSON 是字符串，Redis 管理工具里肉眼可读、排查方便、跨语言；JDK 序列化只有 Java 能读。

#### 套路二：Hash 类型（按字段拆开存取）

```java
// 存：对象 → Map（全 String、无 null）→ Hash
Map<String, Object> userMap = BeanUtil.beanToMap(userDTO, new HashMap<>(),
        CopyOptions.create()
                .setIgnoreNullValue(true)                                  // 丢掉 null 字段
                .setFieldValueEditor((name, value) -> value.toString()));  // 所有值转 String（Hash 的 value 只认字符串）
stringRedisTemplate.opsForHash().putAll("login:token:" + token, userMap);
stringRedisTemplate.expire("login:token:" + token, ttl, TimeUnit.SECONDS);

// 取：Hash → Map → 对象
Map<Object, Object> userMap = stringRedisTemplate.opsForHash().entries("login:token:" + token);
if (userMap.isEmpty()) { ... }   // entries() 永不返回 null（key 不存在时给空 Map），用 isEmpty() 判断
UserDTO userDTO = BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false);
```

`opsForHash()` 常用方法：

| 方法 | 作用 |
| --- | --- |
| `put(key, field, value)` | 写单个字段 |
| `putAll(key, map)` | 整批写入 |
| `get(key, field)` | 读单个字段 |
| `entries(key)` | 读全部（返回 Map，**key 不存在时给空 Map 不是 null**） |
| `delete(key, field)` | 删单个字段 |
| `keySet(key)` | 取所有字段名 |

#### 写不出来时的自救方法

1. IDEA 里敲完 `stringRedisTemplate.opsForValue().` 按 `Ctrl + 空格` → 列出所有方法（试过，没用）
2. 先写伪代码思路（"把 shop 存进 key，1 小时过期"），缺的只是方法名，让 IDE 补全
3. 抄项目里已有例子：发验证码的 `opsForValue().set(key, code, ttl, ...)` 和商铺缓存几乎一样，只是 value 要不要先 JSON 化
4. 存 / 取互逆，写一段顺手把另一段也写了，放一起复习

#### 项目里各场景对号入座

| 场景 | 存法 | 操作器 |
| --- | --- | --- |
| 短信验证码 `login:code:手机号` | 单个值 | `opsForValue()` |
| 登录用户 `login:token:xxx` | 多字段 | `opsForHash()` |
| 商铺缓存 `cache:shop:xx` | 整个 JSON | `opsForValue()` |
| 点赞集合 `blog:liked:xx` | 一堆用户 id | `opsForSet()` |

### 2.4 商铺类型列表缓存（已跑通的完整写法）

缓存逻辑放 Service，Controller 只做"调 Service + 判空"。

`ShopTypeServiceImpl.queryListOrderBySort`：

```java
@Override
public List<ShopType> queryListOrderBySort() {
    // 从 Redis 查缓存
    String cacheShopType = stringRedisTemplate.opsForValue().get(RedisConstants.CACHE_SHOPTYPE_KEY);
    // 判断是否存在
    if (StrUtil.isNotBlank(cacheShopType)) {
        // 存在，直接返回（List 用 toList 还原，不是 toBean）
        return JSONUtil.toList(JSONUtil.parseArray(cacheShopType), ShopType.class);
    }
    // 不存在，查数据库
    List<ShopType> typeList = query().orderByAsc("sort").list();
    // 数据库没有，返回空集合（.list() 永不返回 null，用 isEmpty 判断）
    if (typeList.isEmpty()) {
        return Collections.emptyList();
    }
    // 数据库有，写入缓存（List 整体序列化成 JSON 存）
    stringRedisTemplate.opsForValue().set(RedisConstants.CACHE_SHOPTYPE_KEY,
            JSONUtil.toJsonStr(typeList));
    return typeList;
}
```

`ShopTypeController`：

```java
@GetMapping("list")
public Result queryTypeList() {
    List<ShopType> typeList = typeService.queryListOrderBySort();
    // 判断集合有没有数据，而不是判断是否 null
    if (typeList.isEmpty()) {
        return Result.fail("商店类型不存在");
    }
    return Result.ok(typeList);
}
```

**踩过的坑**：

| # | 坑 | 正解 |
| --- | --- | --- |
| 1 | **key 别拼 List**：`set(CACHE_SHOPTYPE_KEY + typeList, ...)` 会把 List 的 toString 拼进 key，变成 `cache:shop-type:[ShopType(id=1,...)]` 这种怪物 key，读的时候查干净的 `cache:shop-type:`，永远 miss | 列表型缓存的 key 就是常量本身，不拼后缀 |
| 2 | 以为查不到会返回 null，写 `== null` 永远不成立 | `.list()` 查不到返回**空 List**，用 `isEmpty()` |
| 3 | Redis GUI 左侧树按 5 种数据结构分组，长 key 会被截断，容易看错 | 用命令框 `KEYS 前缀*` 看全名 |
| 4 | **key 必须一字不差**：`GET "cache:shop-type"` 返回空，`GET "cache:shop-type:"` 才有值 —— Redis 眼里是两个 key | get / set 永远用同一个常量，别手敲字符串 |
| 5 | 不确定缓存到底生没生效 | 第二次请求看数据库日志，没有 SQL 输出 = 命中；`TTL key` 看剩余秒数（-1 = 永不过期） |

## 三、缓存更新策略

> 缓存不是存进去就不管了 —— 数据库改了，缓存怎么跟着变？三条路，本质是**一致性**和**维护成本**之间的取舍。

### 3.1 三种策略对比

| | **内存淘汰** | **超时删除（TTL 过期）** | **主动更新** |
| --- | --- | --- | --- |
| **说明** | 无需手动维护，依靠 Redis 内存淘汰机制；内存占满时自动淘汰部分 key，下次查询发现缓存丢失，重新查库并更新缓存 | 给 key 设置 TTL，到期自动删除；下一次查询触发缓存重建，查库写入新缓存 | 业务代码控制，**修改数据库的同时操作缓存**（更新 / 删除），主动保证与数据库一致 |
| **一致性** | **差**。只有内存满了才删，数据长期存在，容易产生脏数据 | **一般**。TTL 到期前都是旧数据，存在短暂脏数据窗口 | **好**。数据库变更立刻同步处理缓存，脏数据窗口最小 |
| **维护成本** | **无**，完全依靠 Redis 自带机制，业务不用写额外代码 | **低**，存缓存时额外指定过期时间即可 | **高**，需要在增 / 改 / 删数据库的代码里额外写缓存逻辑，还要考虑失败情况 |

### 3.2 业务场景怎么选

| 一致性需求 | 策略 | 项目里的例子 |
| --- | --- | --- |
| **低** | 使用**内存淘汰**机制 | 店铺类型的查询缓存 |
| **高** | **主动更新**，并以**超时剔除**作为兜底方案 | 店铺详情查询的缓存 |

**一句话选型**：

- **内存淘汰**：兜底用的，不能当更新策略（内存没满就永远不删，一致性最差）
- **超时删除**：成本最低的"基本可用"方案，适合一致性要求不高的数据，通常**再叠一层主动更新**
- **主动更新**：一致性最好，代价是代码要多写，**黑马点评项目走的就是这条**

> 记忆口诀：**想省事就靠 TTL，想要准就自己动手改；内存淘汰只是兜底，不能当饭吃。**

### 3.3 主动更新的三种实现模式

选定"主动更新"后，还要决定**谁来更新、什么时候更新**，业界三种成熟模式：

| 编号 | 模式 | 原文 | 一句话理解 |
| --- | --- | --- | --- |
| **01** | **Cache Aside Pattern**（旁路缓存） | 由缓存的**调用者**，在更新数据库的同时更新缓存 | **业务代码自己动手**，最常用 |
| **02** | **Read/Write Through Pattern**（读写穿透） | 缓存与数据库**整合为一个服务**，由服务维护一致性，调用者无需关心 | **一致性交给中间层**，调用者当甩手掌柜 |
| **03** | **Write Behind Caching Pattern**（异步写回） | 调用者**只操作缓存**，由其它线程**异步**将缓存持久化到数据库，保证**最终一致** | **只写缓存，异步刷库**，性能最高 |

### 3.4 三者对比

| 维度 | Cache Aside | Read/Write Through | Write Behind |
| --- | --- | --- | --- |
| 谁维护一致性 | **调用者**（业务代码） | **缓存服务**（中间层） | **异步线程**（后台任务） |
| 一致性强度 | 强（实时同步） | 强（调用方无感） | **弱，只保证最终一致** |
| 性能 | 一般 | 一般 | **最高**（写缓存就返回） |
| 实现复杂度 | **低**（就几行代码） | 高（要封装服务层 / 组件） | 高（异步线程 + 失败重试 + 丢数据风险） |
| 数据安全 | 较安全 | 较安全 | **有丢数据风险**（缓存宕机、未落库就没了） |
| 典型应用 | **本项目、绝大多数业务系统** | 统一缓存层的中间件产品 | 操作系统 page cache、MySQL Buffer Pool、批量计数 |

**记忆法**：

- **01 Cache Aside** = **自己动手**（旁路：缓存被"绕过"在旁边）
- **02 Read/Write Through** = **找人代劳**（读写都走缓存这层，它替你同步数据库）
- **03 Write Behind** = **先记账后补账**（先写缓存，后台慢慢补库 → 最终一致）

> 本项目采用 **Cache Aside**：实现简单、不引入额外组件，一致性也够用。落到代码上就是**更新数据库后删除缓存**。

### 3.5 操作缓存和数据库的三个问题

**1. 删除缓存还是更新缓存？**

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **更新缓存** | 每次更新数据库都更新缓存 | ❌ **无效写操作较多** |
| **删除缓存** | 更新数据库时让缓存失效，查询时再更新缓存 | ✅ **采用** |

为什么"删"比"改"好：

1. **无效写多**：写多读少的场景，每次写完都改缓存，可能改完根本没人读
2. **并发会乱序**：两个线程同时写，改库顺序和改缓存顺序可能不一致 → 缓存留旧值
3. **删除最简单**：只让缓存失效，下次读时按最新数据重建，逻辑单向

**2. 如何保证缓存与数据库的操作同时成功或失败？**

| 架构 | 方案 |
| --- | --- |
| 单体系统 | 将缓存与数据库操作**放在一个事务**里 |
| 分布式系统 | 利用 **TCC** 等分布式事务方案 |

> ⚠️ **生产实情**：Spring 的 `@Transactional` 只管数据库，**Redis 操作不参与回滚**。所以项目里一般不做强一致，而是 **TTL 兜底 + 失败重试 / 消息队列补偿**，做到**最终一致**。

**3. 先操作缓存还是先操作数据库？**

- 先删除缓存，再操作数据库
- 先操作数据库，再删除缓存

**结论：先更新数据库，再删除缓存**（Cache Aside 的标准姿势），理由见 3.6。极端情况可补一招**延时双删**：删缓存 → 更新数据库 → 延迟几百毫秒再删一次缓存。

| 问题 | 结论 |
| --- | --- |
| 删缓存还是更新缓存 | **删除**（更新缓存会产生大量无效写） |
| 如何保证同时成功 / 失败 | 单体用事务；分布式用 TCC / 消息队列；实际靠 TTL 兜底做到最终一致 |
| 谁先谁后 | **先更新数据库，再删除缓存**（必要时延时双删） |

> 记忆口诀：**"改库不写缓存，改完就把缓存删。"**

### 3.6 线程安全：两种顺序的并发问题

> 两个线程同时读写时，顺序不同，出问题的概率差很多。

#### ① 先删缓存，再更新数据库 —— **概率高** ❌

**情况一（正常）**：数据库和缓存都存 A。

```
线程1：删缓存 → 更新数据库（A → B）
线程2：                          → 缓存未命中 → 查库得 B → 写缓存 B
结果：缓存 B，数据库 B → 一致 ✅
```

**情况二（异常）**：线程之间没加锁，线程二很容易在线程一执行到一半时进来。

```
线程1：删缓存 → [更新数据库很慢，还没完成…]
线程2：           → 未命中 → 查库（还是 A）→ 写缓存 A
线程1：                                        → 更新数据库成功（B）
结果：缓存 A，数据库 B → 不一致 ❌
```

**为什么概率高**：查缓存 + 写缓存比更新数据库**快得多**，线程二很容易抓住"缓存已删、库里还是旧值"这个空档。

#### ② 先更新数据库，再删缓存 —— **概率极低** ✅

要出问题，必须同时满足两个条件：**缓存刚好失效**，且**读线程在"查完库、还没写完缓存"的极短间隙里，写线程完成了"更新库 + 删缓存"**。

```
线程1（写）：                                  更新数据库（A → B）→ 删缓存
线程2（读）：缓存刚好过期 → 未命中 → 查库得 A →（准备写缓存）→ 写缓存 A
结果：缓存 A，数据库 B → 不一致 ❌（但窗口极小）
```

**为什么概率极低**：从"查库"到"写缓存"这段间隔非常短，写线程要恰好在这个窗口内完成"更新数据库 + 删除缓存"两件事，几乎不可能。

#### 结论

| 顺序 | 出问题的概率 | 是否采用 |
| --- | --- | --- |
| 先删缓存，再更新数据库 | **高**（更新库慢，空档大） | ❌ |
| **先更新数据库，再删缓存** | **极低**（窗口极小） | ✅ 采用 |

> 一句话：**先改库、再删缓存**；对一致性要求极高时，再叠加**延时双删**或**消息队列**补偿。

## 四、缓存穿透

### 4.1 是什么

**客户端请求的数据在缓存中和数据库中都不存在**，这样缓存永远不会生效，请求会全部打到数据库。

举例：客户端随便发一个请求（既不在缓存、也不在库里）—— 先去缓存找，没有；再去库里找，也没有；返回客户端。客户端继续重复，成千上万个这样的请求，就把数据库打垮了。

### 4.2 解决方案一：缓存空对象

**实现思路**：请求进来，缓存没有 → 查数据库也没有 → 数据库返回 null，**Redis 把这个 null 也缓存起来**。下次同样的请求再来，直接在缓存里查到 null（命中），就不会一直打到数据库。

**改造前后的流程差异**：

```
【原来】缓存未命中 → 查库 → 判断是否存在 → 不存在直接返回 404 → 结束

【现在】缓存未命中 → 查库 → 判断是否存在
                          ├─ 不存在 → 把空值写入缓存 → 返回"店铺不存在"
                          └─ 存在   → 写缓存 → 返回商铺信息
       缓存命中 → 判断值是否为空
                          ├─ 不为空 → 返回商铺信息
                          └─ 为空   → 直接结束（返回"店铺不存在"）
```

**业务层代码**：

```java
@Override
public Result queryById(Long id) {
    // 1. 从 Redis 查询商铺缓存
    String shopJson = stringRedisTemplate.opsForValue().get(RedisConstants.CACHE_SHOP_KEY + id);

    // 2. 判断是否命中（isNotBlank 对 null 和 "" 都返回 false，所以能顺带过滤掉"空值缓存"）
    if (StrUtil.isNotBlank(shopJson)) {
        // 3. 命中真实数据，直接返回
        Shop shop = JSONUtil.toBean(shopJson, Shop.class);   // JSON 字符串 → Shop 对象
        return Result.ok(shop);
    }

    // 2.1 走到这里只剩两种情况：null（没缓存） 或 ""（缓存了空对象）
    if (shopJson != null) {
        // 命中空值缓存 → 说明之前查过数据库也没有，直接返回不存在
        return Result.fail("店铺不存在");
    }

    // 4. 未命中，根据 id 查询数据库
    Shop shop = getById(id);

    // 4.1 数据库也不存在 → 缓存空值（Redis 没有 null，用 "" 代替），并设置短 TTL
    if (shop == null) {
        stringRedisTemplate.opsForValue().set(RedisConstants.CACHE_SHOP_KEY + id, "",
                RedisConstants.CACHE_NULL_TTL, TimeUnit.MINUTES);
        return Result.fail("店铺不存在");
    }

    // 4.2 存在 → 写入 Redis（对象转 JSON）
    stringRedisTemplate.opsForValue().set(RedisConstants.CACHE_SHOP_KEY + id,
            JSONUtil.toJsonStr(shop), RedisConstants.CACHE_SHOP_TTL, TimeUnit.MINUTES);

    // 5. 返回
    return Result.ok(shop);
}
```

> ⭐ **这段代码的灵魂是"两次判断"**：
> - `StrUtil.isNotBlank(shopJson)` → 只认**有内容的字符串**，`null` 和 `""` 都返回 false → 所以它只能判断"**有没有真实数据**"
> - `shopJson != null` → 走到这里说明值不是 null 而是 `""` → 说明**之前缓存过空对象**
>
> 顺序不能反：先用 `isNotBlank` 拦掉真实数据，再用 `!= null` 区分"缓存了空值"和"根本没缓存"。

**优点**：

- 实现简单，维护方便

**缺点**：

- **额外的内存消耗** → 解决办法：缓存 null 时**加一个 TTL**，到期自动清掉
- **可能造成短期的不一致** → 一开始这个 id 不存在，缓存了 null；刚好后面这个 id 被注册了、数据存在了，此时读到的还是 null，**短期数据不一致**

### 4.3 解决方案二：布隆过滤

**做法**：在客户端和 Redis 缓存之间再加一层**布隆过滤器**。客户端请求先经过它，过滤器判断"数据存在吗"——

- 判断**不存在** → 直接拒绝，不再往下访问
- 判断**存在** → 放行，继续走原来的缓存 / 数据库流程

**原理**：

布隆过滤器本质是一个 **byte 数组，里面存的是二进制位（0 / 1）**。

1. 判断数据是否存在时，**并不是真的把数据存进去**，而是把这些数据用某几种哈希算法算出哈希值
2. 把哈希值映射成数组下标，把对应位置**置为 1**
3. 后面再判断时，就看对应位置的位是 **0 还是 1**

**它是一种概率上的统计，不是百分百准**：

| 判断结果 | 可信度 |
| --- | --- |
| 说不存在 | **一定不存在**（位是 0，说明从没被任何数据置 1） |
| 说存在 | **不一定真的存在**（可能是别的数据把这个位置也置了 1 → **误判**） |

**优点**：

- 内存占用较少，没有多余 key

**缺点**：

- **实现复杂**
- **存在误判可能**

### 4.4 两种方案对比

| 维度 | 缓存空对象 | 布隆过滤 |
| --- | --- | --- |
| 实现难度 | **简单**，几行代码 | 复杂，要引入 / 维护过滤器 |
| 内存占用 | 每个不存在的 key 都要存一条（靠 TTL 清） | **少**，一个位数组搞定 |
| 准确性 | **准确**，不会误判 | 有**误判率**（说不存在一定不存在，说存在可能误判） |
| 数据新增 | 新数据进来会有短期不一致（缓存的 null 挡住） | 数据新增要**同步维护过滤器**，否则新 id 会被误判为不存在 |
| 适用场景 | 空查询量不大、想快速上线 | 海量恶意请求、key 空间可预知 |

> 项目里先用**缓存空对象**（简单够用），布隆过滤器是对量级更大、更极端场景的加固。

## 五、面试考点

### Q1：缓存的作用和成本是什么？什么数据适合缓存？

**答**：作用 —— 降低后端负载、提高读写效率、降低响应时间。成本 —— **数据一致性**（缓存和库会不同步）、**代码维护**（多一套读写逻辑）、**运维**（多一个中间件）。

适合缓存的数据：**读多写少、对一致性要求不高、能够容忍短暂不一致**的数据（店铺详情、类型列表）。强一致的资金类数据不适合直接放缓存。

### Q2：缓存穿透是什么？怎么解决？

**答**：请求的数据**缓存和数据库都不存在**，缓存永远不生效，请求全部打到数据库（常见于恶意用不存在的 id 刷接口）。

解决方案：

1. **缓存空对象** —— 查库为空也缓存一个空值（加短 TTL），下次直接命中。简单，但占内存、有短期不一致
2. **布隆过滤器** —— 在缓存前拦截，判断不存在直接拒绝。省内存，但有误判率、实现复杂

### Q3：缓存空对象为什么要加 TTL？

**答**：两个原因 ——

1. **省内存**：不加 TTL 的话，每个被刷的假 id 都会在 Redis 里留一条记录，越积越多
2. **修正不一致**：如果这个 id 后来真的被注册了，缓存里的空值会挡住正确数据，TTL 到期后能自动恢复

### Q4：布隆过滤器为什么会有误判？为什么"说不存在一定不存在"？

**答**：布隆过滤器用多个哈希函数把数据映射到位数组的多个位置并置 1。

- 判**不存在**：只要有一个位置是 0 → 这个数据从来没被写入过 → **一定不存在**（可靠）
- 判**存在**：所有位置都是 1 → 但这些 1 可能是**别的数据**置的 → 只能推测"可能存在" → **有误判**

误判率随插入数据量增大而升高，且**不支持删除**（删了会影响别的数据）。

### Q5：缓存更新策略有哪三种？分别适合什么场景？

**答**：

| 策略 | 一致性 | 维护成本 | 场景 |
| --- | --- | --- | --- |
| 内存淘汰 | 差 | 无 | 低一致性（店铺类型列表） |
| 超时删除（TTL） | 一般 | 低 | 一般都用，做兜底 |
| 主动更新 | 好 | 高 | 高一致性（店铺详情） |

### Q6：为什么是"删除缓存"而不是"更新缓存"？

**答**：更新缓存有三个问题 ——

1. **无效写多**：写多读少时，改完缓存可能根本没人读
2. **并发乱序**：两个线程改库顺序和改缓存顺序可能不一致，缓存留下旧值
3. **逻辑复杂**：删除只是"让缓存失效"，下次读自然重建，单向简单

### Q7：先删缓存还是先删数据库？为什么？

**答**：**先更新数据库，再删除缓存**。

- **先删缓存再改库**：删完缓存、库还没更新完，此时读请求进来会读到**旧值**并写回缓存，窗口大、**概率高**
- **先改库再删缓存**：要出问题必须"缓存刚好失效 + 读线程恰好在查库与写缓存之间的极短间隙"，**概率极低**

极端一致性要求可以再加**延时双删**（删缓存 → 改库 → 延迟再删一次）或**消息队列**补偿。

### Q8：Cache Aside、Read/Write Through、Write Behind 有什么区别？

**答**：

- **Cache Aside**：调用者自己维护缓存和数据库，最常用
- **Read/Write Through**：缓存与数据库合成一个服务，由服务保证一致性，调用者无感
- **Write Behind**：只写缓存，异步刷库，性能最高但**只保证最终一致**，有丢数据风险

### Q9：怎么验证缓存到底生效了？

**答**：第二次请求看数据库日志有没有 SQL 输出（没有 = 命中）；或用 `TTL key` 看剩余时间（-1 表示没设过期）。另外注意 key 必须和写入时**一字不差**（多一个冒号就是另一个 key）。

### Q10：缓存穿透和缓存击穿、缓存雪崩有什么区别？

**答**（本日只学了穿透，另两个是常见追问，先记住区别）：

| 名称 | 数据状态 | 后果 |
| --- | --- | --- |
| **穿透** | 数据**根本不存在**（库和缓存都没有） | 每次请求都打到库 |
| **击穿** | 数据**存在**，但缓存**刚好过期** | 大量请求同时打库重建 |
| **雪崩** | **大量 key 同时过期**或 Redis 宕机 | 整体流量瞬间压到库 |

## 六、今日重点

### 6.1 必记 5 件事

1. **缓存三件事**：怎么加（读缓存 + 未命中回填）、怎么改（**删**缓存不是改缓存）、怎么防（防止打穿数据库）。
2. **操作器必须配对**：`opsForValue` / `opsForHash`，存和取用同一个；String 存对象必须 JSON 序列化。
3. **更新策略选型**：低一致性用内存淘汰（+TTL），高一致性用主动更新 + 超时剔除兜底。
4. **主动更新 = Cache Aside = 先改库、再删缓存**（概率最低的脏数据方案）。
5. **缓存穿透两招**：缓存空对象（简单，要加 TTL）、布隆过滤器（省内存，但会误判）。

### 6.3 易错点清单

| ❌ 易错 | ✅ 正确 |
| --- | --- |
| 用 `== null` 判断"有没有数据" | `StrUtil.isNotBlank()` 判真实数据，`!= null` 判空值缓存，两步都要 |
| 缓存空对象不设 TTL | 必须设短 TTL，否则无限膨胀 + 挡住后来的真数据 |
| 缓存 key 拼 List / 拼对象 | key 只用常量，拼接会造出永远 miss 的怪物 key |
| 先删缓存再改库 | 先改库再删缓存（概率低得多） |
| 把"更新缓存"当成更好的方案 | 更新缓存无效写多、并发易乱序，优先**删除** |
| 以为布隆过滤器百分百准 | 说不存在一定不存在，**说存在可能误判** |
| `.list()` 判 null | `.list()` 返回空集合，用 `isEmpty()` |
