### Q4 `#{}` 和 `${}` 的区别 ⭐ 基础必背

**一句话**：`#{}` 是预编译占位符，`${}` 是字符串拼接。

| | `#{}` | `${}` |
| --- | --- | --- |
| 底层 | 生成 `?`，走 `PreparedStatement.setXxx()` | 直接替换成字面量，拼进 SQL |
| SQL 注入 | 防（参数被当值，不当语法） | **不防**（用户输入会变成 SQL 的一部分） |
| 加引号 | 自动加，字符串不用手写 `''` | 不加，字符串要自己写引号 |
| 性能 | 同结构 SQL 能复用执行计划 | 每次都是新 SQL，无法复用 |

**例子**：

```java
@Select("SELECT * FROM user WHERE username = #{name}")
// 传 name = "a' OR '1'='1"  → 只是一个普通字符串，查不到东西

@Select("SELECT * FROM user WHERE username = '${name}'")
// 传 name = "a' OR '1'='1"  → WHERE username = 'a' OR '1'='1'  → 全表返回
```

**`${}` 什么时候必须用**：表名、列名、`ORDER BY` 后面的字段名这类**语法的一部分**，占位符没法替代。

```java
// 表名用 ${}，参数用 #{}
@Select("SELECT * FROM ${tableName} WHERE id = #{id}")
```

用 `${}` 传表名/列名时**必须做白名单校验**，否则照样能注入。

**结合项目**：MyBatis-Plus 的 `apply("season & {0} > 0", season)` 里那个 `{0}` 是安全占位符，内部会转成 `#{}`，不是字符串拼接。所以位运算这种原生 SQL 片段也能安全传参。

### Q5 `@TableLogic` 逻辑删除是怎么实现的？有什么坑？

**原理**：MyBatis-Plus 解析实体时识别到 `@TableLogic` 注解的字段，然后在自动生成的 SQL 里做两件事：

| 操作 | 实际 SQL |
| --- | --- |
| `deleteById(id)` | `UPDATE clothing SET deleted = 1 WHERE id = ? AND deleted = 0` |
| `selectById(id)` | `SELECT ... WHERE id = ? AND deleted = 0` |
| `selectPage(...)` | `SELECT ... WHERE deleted = 0 AND ...` |
| `updateById(...)` | `UPDATE ... WHERE id = ? AND deleted = 0` |

**一句话**：删除变成 UPDATE，所有查询自动追加 `deleted = 0`。

**五个坑**（面试爱追问）：

1. **唯一索引冲突**：账号逻辑删除后（`deleted=1`），同名再注册会撞 `uk_username`。因为查询查不到（自动带 `deleted=0`），但 insert 时记录还在表里。
2. **手写 SQL 不管**：XML 或 `@Select` 里自己写的 SQL 不会自动加 `deleted = 0`，要手动写。
3. **从属数据要手动清**：主表逻辑删了，关联表（如 `clothing_tag`）的记录还在，会变成孤儿数据。这就是为什么删除衣物时要在同一个事务里清标签。
4. **表越来越大**：数据永远不真删，数据量大时要归档或定期物理清理。
5. **`deleteById` 返回的是 UPDATE 影响行数**，不是"删了几条记录"。

**结合项目**：`clothing`、`outfit` 都有 `deleted`，`clothing_tag` 故意**不加**——它走"先按 clothing_id 全删、再整批插"的物理删除，如果做成逻辑删除，旧标签会留在表里被下次查询捞出来，出现重复。

### Q6 MyBatis-Plus 分页插件是怎么实现的？ ⭐ 今日重点

**核心结论**：分页**必须配 `PaginationInnerInterceptor`**，不配的话 `selectPage` 不分页，会把全表数据捞回来。

**原理**：基于 MyBatis 的 `Interceptor`（插件）机制，拦截 `Executor.query` 方法。执行前判断参数里有没有 `IPage` 类型的对象，有的话做三件事：

1. **先查总数**：把原 SQL 包一层 `SELECT COUNT(*) FROM (原SQL) tmp`，为了性能会先去掉 `ORDER BY`
2. **再拼分页**：给原 SQL 加上 `LIMIT offset, size`
3. **塞回结果**：把查到的 `List` 和 total 一起放进 `IPage` 对象返回

**所以一次 `selectPage` 调用，实际发了两条 SQL**：

```sql
SELECT COUNT(*) FROM clothing WHERE deleted = 0 AND user_id = 2
SELECT * FROM clothing WHERE deleted = 0 AND user_id = 2 ORDER BY create_time DESC LIMIT 0, 6
```

**关键点**：

- `offset = (current - 1) * size`，`current` 从 **1** 开始，不是 0
- 返回的 `Page` 对象自带 `records / total / size / current / pages`，直接返回给前端就够用
- 只对**一次**查询生效，一个方法里查两次要传两个 `Page`

**坑**：

- 忘了配插件 → 不报错，只是不分页，数据一多直接卡死（这是最隐蔽的）
- `Page` 对象的泛型要和方法返回类型一致，`Page<Object>` 传给需要 `Page<Clothing>` 的方法会编译报错
- 深分页（`LIMIT 100000, 10`）性能差，MySQL 要扫前 10 万行，数据量大时要改用"游标分页"（`WHERE id > 上一页最后一个id`）

#### 面试模板

> MyBatis-Plus 的分页靠 `PaginationInnerInterceptor` 这个内置拦截器实现，原理是 MyBatis 的插件机制拦截 `Executor.query`。
> 它在执行前判断参数里有没有 `IPage`，有就先拿原 SQL 生成 count 语句查总数（会去掉 order by 优化），再给原 SQL 拼上 `LIMIT offset, size`，最后把结果和 total 一起塞回 `IPage`。
> 所以一次分页查询是两条 SQL。
> 需要注意的是一旦忘了配置这个拦截器，`selectPage` 不会报错，只是退化成查全部，数据量一大就出问题——我在项目里就是先在 `MybatisPlusConfig` 里注册好才开始写分页的。
