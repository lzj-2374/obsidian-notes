## 第 1 天 · 10-28 · Spring 事务

### Q1 `@Transactional` 是怎么生效的？ ✅ 已掌握

**模板**：

`@Transactional` 基于 **AOP 动态代理**实现。Spring 启动时给带注解的 Bean 生成代理对象，代理里有一个 `TransactionInterceptor`。方法调用进来后，拦截器先通过事务管理器（`PlatformTransactionManager`，MySQL 场景是 `DataSourceTransactionManager`）调用 `getTransaction()` 获取连接、关闭自动提交；然后执行目标方法；正常返回就 `commit`，抛异常就按 `rollbackFor` 规则 `rollback`；最后把连接归还连接池。

**关键**：事务的开启和提交都发生在**方法体之外**（代理层）。

**两个延伸结论**：
1. 事务边界在代理层 → `synchronized` 写在方法内部时，锁在事务里，释放早于提交（Day08 那个坑）
2. 连接通过 ThreadLocal 绑定当前线程 → 事务不能跨线程

### Q2 事务失效的场景有哪些？ ⭐ 今日重点

**口诀：自调用、非 public、异常吞、异常类型、没托管、跨线程**

| # | 场景 | 为什么失效 | 解决 |
| --- | --- | --- | --- |
| 1 | **自调用**：同类里 `this.methodB()` 调 `@Transactional` 方法 | `this` 是原始对象，绕过代理，拦截器不执行 | `AopContext.currentProxy()` / 注入自身 / 拆到另一个 Bean |
| 2 | **方法不是 public** | Spring 事务属性只对 public 方法生效，非 public 直接不代理 | 改成 public |
| 3 | **异常被 catch 吞掉** | 方法正常返回，拦截器看不到异常，认为成功 → commit | catch 后重新抛出，或 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |
| 4 | **异常类型不匹配** | 默认只回滚 `RuntimeException` 和 `Error`，受检异常不回滚 | `@Transactional(rollbackFor = Exception.class)` |
| 5 | **类没被 Spring 管理** | 自己 `new` 的对象没有代理 | 交给 Spring 管理（`@Service`） |
| 6 | **跨线程** | 事务上下文绑定 ThreadLocal，新线程拿不到同一连接 | 不要在子线程里做同一事务的操作 |
| 7 | **数据库引擎不支持**（MyISAM） | 引擎本身没事务 | 用 InnoDB（现在默认） |

**背这 5 个就够**：自调用、非 public、异常被吞、异常类型、跨线程（1~4 + 6）。

**结合项目的一句话**（加分项）：

> 我在做一人一单时踩过自调用的坑——在 `seckillVoucher` 里直接 `this.createVoucherOrder()`，事务不生效；改成 `AopContext.currentProxy()` 通过代理调用才生效，而且为了让锁包住事务，锁加在外层无事务的方法上。

## 第 2 天 · 10-29 · Spring 事务传播行为

### Q3 事务传播行为 (Propagation) ⭐ 今日重点

**定义**：两个带事务的方法嵌套调用时，内层方法是「加入外层事务」还是「自己新开一个」——由传播行为决定。

#### 先理解：一个事务 = 一个连接 = 一本草稿本

同一个本子上写的字，撕本子就一起消失。所以关键问题是：**内层方法在哪本本子上写？**

| 内层怎么写 | 用哪本 | 结果 |
| --- | --- | --- |
| `@Transactional`（默认 REQUIRED） | **外层那本**（加入外层事务） | 外层回滚 → 内层一起没 |
| **不加 `@Transactional`** | **还是外层那本**（同线程，连接还在 ThreadLocal） | 一样一起没 ❌ 最常见的误解 |
| `REQUIRES_NEW` | **自己另拿一本**（外层那本挂起） | 外层回滚，内层的还在 |

**回滚的触发是「异常传到外层方法体」**，被外层的事务拦截器捕获才回滚。所以只换本子不够，外层还要 `try-catch` 把异常吃掉。

#### 核心场景（面试最爱问）

```java
@Transactional
public void createOrder() {      // A：插入订单
    orderMapper.insert(order);
    otherService.addPoints();    // B：加积分，抛异常
}
```

**默认（REQUIRED）下：会一起回滚。** 因为 B 加入 A 的事务，用的是**同一个连接**，A 和 B 共用一个事务，异常抛到 A，整个事务回滚。

**⚠️ 关键纠正**：把 B 的 `@Transactional` 去掉 ≠ 隔离。B 不加事务，它仍然在 A 的事务里执行（用的还是 A 的连接），A 回滚 B 照样回滚。

**要「B 失败不影响 A」必须两件事一起做**：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)   // ① 开独立事务
public void addPoints() {
    ...
    throw new RuntimeException();   // ② A 里还要 try-catch 包住
}
```

1. `REQUIRES_NEW`：B 开新事务，A 的事务被**挂起**（从连接池另取一个连接）
2. **A 里必须 `try-catch`**：否则异常传播到 A，A 依然回滚——这一步很多人漏掉

> 注：这里用 `REQUIRES_NEW` 是为了把「独立事务」讲最直白。如果业务上「外层失败时内层也不该留下」（如下单加积分），应该用 `NESTED`——内层共用外层连接，只回滚到保存点。选型见下方口诀。

#### 7 种传播行为

| 传播行为 | 行为 | 用不用 |
| --- | --- | --- |
| **REQUIRED**（默认） | 有事务就加入，没有就新建 | ⭐ 90% 场景 |
| **REQUIRES_NEW** | 总是新建真事务，挂起外层 | ⭐ 日志、审计、操作记录等「无论外层成败都要留」的数据 |
| **NESTED** | 嵌套（savepoint 保存点），共用外层连接 | ⭐ 下单+加积分、下单+扣券等「外层失败就不该留下」的子操作 |
| SUPPORTS | 有就加入，没有就以非事务方式跑 | 少用 |
| NOT_SUPPORTED | 非事务方式跑，挂起外层 | 少用 |
| MANDATORY | 必须已有事务，否则抛异常 | 少用 |
| NEVER | 必须没有事务，否则抛异常 | 少用 |

**记 3 个就够：REQUIRED / REQUIRES_NEW / NESTED。**

**选型口诀**：问自己「主流程最后失败了，子操作的数据该不该还在？」——该留用 `REQUIRES_NEW`，不该留用 `NESTED`。

⚠️ 反例：加积分用 `REQUIRES_NEW` 会导致「订单回滚了，积分却加上了」的脏数据，应该用 `NESTED`。

#### REQUIRES_NEW vs NESTED（易混）

|  | REQUIRES_NEW | NESTED |
| --- | --- | --- |
| 连接 | 新开一个（外层挂起） | 共用外层连接 |
| 实现 | 新事务 | savepoint 保存点 |
| 外层回滚 | 内层也回滚（已提交的独立事务除外） | 内层一起回滚 |
| 内层回滚 | 不影响外层 | 不影响外层（外层要 catch） |
| 风险 | 连接池小可能死锁（两个连接互相等） | 只支持 `DataSourceTransactionManager` |

#### 面试模板

> 传播行为解决的是「事务嵌套时，内层方法怎么处理事务」。
> 默认 `REQUIRED`：有事务就加入，没有就新建——所以内外层共用一个连接、一个事务，内层抛异常外层一起回滚。
> 如果希望内层失败不影响外层，用 `REQUIRES_NEW`：内层开独立事务、外层挂起，**同时外层要 catch 住异常**，否则异常照样传出去让外层回滚。
> 还有一个 `NESTED`，用 savepoint 实现，共用连接、只回滚到保存点，但只支持 JDBC 事务管理器。
> 项目里下单主流程用的是默认 REQUIRED，像记日志、加积分这种不希望影响主流程的操作可以用 REQUIRES_NEW。
